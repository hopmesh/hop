Core Protocol · grade A
lowcore-protocol-r3-01Always-spool durably retains private ACK bundles too, growing relay spool setriskS
Evidence
emit_private_ack builds the ACK with Some(crypto::mailbox_route(...)) toward the sender (node.rs:1774), so spoolable_private_bundles (node.rs:3239 accepts any private bundle with a mailbox) will also durably spool return-path ACKs, not just forward messages
Impact
A relay holds more durable private bundles than strictly necessary (ACKs are usually short-lived); bounded by the store eviction cap and TTL, so it is a storage-efficiency cost, not a correctness or delivery defect
Fix
Optionally distinguish forward-content from ACK payloads when deciding spoolability, or document that ACK spooling is intentional for the P4/P5 return path (it aids delivery-confirmation resilience). No code change required for correctness.
lowcore-protocol-r3-02Vaccine seen-gate leaves a narrow target-arrives-after-vaccine purge gapriskM
Evidence

Impact
A rare arrival-ordering race leaves one relay carrying a delivered bundle until its (clamped) TTL; the target still expires. This ordering was also unhandled before the dedup change (the scan only ran on vaccine arrival, never on target arrival), so it is not a regression

Persistence / Stores · grade A
mediumstores-r3-01Handoff/spool durable expireAt is derived from sender created_at in node.rs, bypassing the stores-r2-01 guaranteeriskS
Evidence
node.rs:3212 `let expires = b.inner.created_at.saturating_add(b.inner.lifetime_ms as u64);` in undeliverable_device_bundles and the identical node.rs:3257 in spoolable_private_bundles; these `expires` values flow to Presence::put_bundle_to (relayd main.rs:1275) and spool_to_mailbox (main.rs:1388) and become the Firestore `expireAt` TTL field via doc_json.
Impact
stores-r2-01 fixed exactly this created_at(0)+lifetime -> ~1970 anti-pattern INSIDE the store, but the relay's handoff and §39 spool durable writes recompute expiry from the same advisory created_at without consulting the store's receiver-anchored seen_expiry. A relayed bundle whose original sender stamped created_at=0 (the wire/BundleOpts default, and any non-node or hostile sender) gets a durable expireAt in the past, so the TTL policy sweeps a still-live handed-off/spooled message and an offline recipient silently loses it. Node-originated sends stamp real now_ms so the mainline is safe, which keeps this a risk rather than a mainline critical.
Fix
Have undeliverable_device_bundles/spoolable_private_bundles source expires from self.store.seen_expiry(&id) (the same clamped receiver-anchored deadline the store mirrors), falling back to now_ms+lifetime only if absent, so every durable expireAt is receiver-anchored exactly like stores-r2-01. (Cross-area: fix lands in core/hop-core/src/node.rs.)
lowstores-r3-02Rehydrate 'expires==0 means never-expire' branch is contradicted by prune semantics and is effectively deadgapS
Evidence
hop-store-firestore/src/lib.rs:258 `let expires = if expires == 0 { 0 } else { ... }` then put_with_expiry(bundle, 0); but MemoryStore::prune (store.rs:247) drops any id where `exp <= now_ms`, and 0 <= now_ms is always true, so a 0-expiry rehydrated bundle is wiped on the first real-clock prune (~1s after cold start).
Impact
The documented 'never-expire' contract is false: a stored expiry of 0 would be reaped immediately, not kept forever. In practice unreachable (every live writer computes now_ms+lifetime with a real relay clock and non-zero default lifetime, so expires is never 0), so no live data loss - but the branch and its comment (lib.rs:256) are misleading and untested (rehydrate_preserves_the_stored_expiry_anchor never prunes a 0 case).
Fix
Either drop the special-case and let any stored expiry flow through the clamp, or if a true sentinel is wanted, map 0 to u64::MAX (real never-expire) and add a test that prunes past 'now' and asserts the 0/sentinel bundle survives.

mediumsecurity-privacy-r3-01Sparse-deployment (<2^16 nodes) prefix bucket is effectively a per-address reachability disclosureriskL
Evidence
crypto.rs:447-461 (security-privacy-r2-03) documents it plainly: MAILBOX_ROUTE_PREFIX_BYTES=2 is a COMPILE-TIME constant, so below ~65k reachable addresses "a target's bucket is almost always occupied by the target ALONE ... seeing the bucket active is, with near-certainty, a per-address reachability disclosure". The current fleet is single-digit devices.
Impact
Against an address-knower observing a routing/spool bucket in a region, the '2-byte prefix anonymity set' provides no meaningful anonymity at real-world deployment sizes; the mitigation only keeps routing keys from being unique on the wire. This is the core §39 metadata-privacy promise degrading to near-zero at current scale.
Fix
Widen k adaptively as observed reachable-N grows (so ~N/2^k stays >= a target set size). This is wire-affecting (the header carries the prefix width), so it needs a versioned format change; it is correctly deferred and tracked. mediumsecurity-privacy-r3-02Pure-P2P (no relay) prefix collision still black-holes a passive recipient behind an active decoygapM
Evidence
The forward gate suppresses the flood fallback when a colliding live gradient exists but this link isn't a next-hop: offer_one_to_link node.rs:4696 `if any_live && !this_link_is_a_next_hop { return; }`. The always-spool fix (node.rs:3255) is the ONLY recovery path, and spoolable_private_bundles + take_wanted_mailboxes are drained only by hop-relayd (services/hop-relayd/src/main.rs:652-653). No non-relay node runs the want-beacon spool-reload loop.
Impact
In a pure device-to-device deployment with no relay in the partition (the current fleet is P2P-test-phase with relays deployed-off), a private bundle to a passive/offline recipient whose 2-byte prefix collides with a nearby active recipient can dead-end: the directed copy rides only the decoy's link (dropped on recognition) and the flood is suppressed. The test a_passive_colliding_recipient_is_not_black_holed (node.rs:6681) proves recovery ONLY via a relay's spool + B2's later want-beacon, not P2P.
Fix
Either (a) also suppress-with-spool on any node (surface spoolable_private_bundles/take_wanted_mailboxes through the driver so a P2P carrier can reload), or (b) do not suppress the flood fallback for a bundle whose intended recipient is NOT provably in the live next-hop set - i.e. keep one flood copy alive when the bucket is a prefix anonymity set of size>1. Document the current relay-dependency of the black-hole fix in DESIGN.md.
lowsecurity-privacy-r3-03Legacy plaintext Android mirrors are read-once but the transitional window leaves cleartext on diskriskS
Evidence
HopBearer.kt:956 and :964 fall back to reading a legacy plaintext blob when MirrorCrypto.open returns null (`?: blob` / `?: String(blob)`), and isSealed distinguishes by magic (MirrorCrypto.kt:29). An upgraded install's existing messages.json/contacts.json stays plaintext on disk until the next debounced rewrite reseals it.

lowsecurity-privacy-r3-04Vaccine resolve scan is O(held private bundles) per unique token; a distinct-token flood within the rate cap still costs CPUriskM
Evidence
resolve_vaccine_target iterates self.store.have().ids doing a DH+hash per held private bundle (node.rs:1597-1611). It runs once per UNIQUE vaccine id (seen-gated) but the per-link cap is MAX_PRIV_BUNDLES_PER_WINDOW=256 (node.rs:244), so up to 256 distinct-token vaccines/window/link each trigger a full scan.
