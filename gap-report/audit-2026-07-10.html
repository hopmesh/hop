What the remediation broke (10)

Findings the re-audit marked as newly introduced by the fix-everything-to-A push. Trading one bug for another is the risk of a fast, broad remediation.
medium↻ regressioncore-protocol-r2-01M
Finding
Prefix-bucket collision can silently starve a passive recipient when a colliding recipient is active
Evidence
The private forward gate skips all non-gradient links once a bucket has ANY live next-hop: node.rs:4598 'if any_live && !this_link_is_a_next_hop { return; }'. The spool gate also refuses to spool when a live gradient exists for the route: node.rs:3180-3187 'let live = self.recv_gradient.get(&route)...; if live { continue; }'. Buckets key on the 2-byte prefix (route_key, node.rs:220). If recipient A (passive/offline) and recipient B (actively beaconing) share the prefix bucket, a bundle for A rides ONLY B's link, B fails the per-message recognition tag and drops it, and A never receives it AND it is not spooled.
Fix
When a private bundle is steered down a gradient bucket but the intended recipient is NOT the beaconing next-hop, still keep an epidemic-flood fallback (or a spool) rather than suppressing it entirely. E.g. always ALSO spool a private bundle whose route bucket is live-but-may-be-a-collision, or flood it low-rate on non-gradient links so a passive colliding recipient still sees it. At minimum add a test that constructs two addresses colliding on the 2-byte prefix and asserts both receive their own message.
medium↻ regressioncore-protocol-r2-03M
Finding
Token-only vaccine triggers an un-rate-limited O(held-bundles) store scan on every duplicate flood copy
Evidence
resolve_vaccine_target scans the whole store, doing a DH-derived tag compare per held private bundle: node.rs:1578-1591 'for id in self.store.have().ids { ... recognition_tag_from_shared(token, &id) == tag }'. It is called from the vaccine branch node.rs:4166 which runs for every is_ack Vaccine arrival, BEFORE any store.seen dedup (the only dedup, store.put at node.rs:4202, runs AFTER). Vaccines have private: None (bundle.rs:504) so they are NOT covered by the F-07 private-ingest rate limit (node.rs:3810 gates only bundle.is_private()). A forged vaccine passes verify() trivially: verify only checks compute_vaccine_id(token)==id (bundle.rs:576-582), which an attacker satisfies by setting id from a random token.
Fix
Gate the vaccine block behind a seen/immune check so a duplicate or already-processed vaccine short-circuits before resolve_vaccine_target, and/or apply a per-link rate limit to unsigned Vaccine bundles (extend allow_private_ingest to cover Destination::Vaccine). Maintain a small cache of recently-resolved/negative tokens to avoid re-scanning for a token that matched nothing.
medium↻ regressioncore-ffi-sdk-r2-02S
Finding
Feature-gate mismatch: `cargo build -p hop --no-default-features` fails to compile
Evidence
lib.rs:21-22 `#[cfg(not(feature = "minimal"))] type HopStore = hop_store_sqlite::SqliteStore;` but Cargo.toml gates the dependency behind `full` only (`full = ["dep:uniffi", "dep:hop-store-sqlite"]`; `minimal = []`). `full` and `minimal` are independent cargo features, so with neither set, `not(minimal)` is true yet `hop_store_sqlite` is not compiled.
Fix
Gate the sqlite alias and open_store_persistent/open_node_inner on `feature = "full"` (and the MemoryStore alias on `not(feature = "full")`), OR make `minimal` explicitly `= ["..."]`-exclusive and add a `compile_error!` guard when neither full nor minimal is set.

medium↻ regressionapple-r2-03M
Finding
.completeFileProtection can silently drop a locked-screen background receive from the UI history mirror
Evidence
HopBearer.swift:1684 messages.json is written with [.atomic, .completeFileProtection]; applyInbox appends inbound messages (1098) which triggers scheduleMessageSave. A background receive while the device is LOCKED cannot write a completeFileProtection file (data protection denies it), and takeInbox already drained the node inbox, so the message exists only in the in-memory array.
Fix
Use .completeFileProtectionUntilFirstUnlock for messages.json/channels.json/contacts.json so background writes succeed after the first post-boot unlock, or rebuild the UI history from the node store on load instead of relying solely on the JSON mirror.

medium↻ regressionsecurity-privacy-r2-01M
Finding
Token-only vaccine (wire v3) added an un-deduped per-arrival scan and forged vaccines still amplify
Evidence
node.rs:4165 Destination::Vaccine(token) => resolve_vaccine_target(&token) runs on EVERY vaccine arrival with NO store.seen dedup in front of the is_ack block (node.rs:4148); resolve_vaccine_target (node.rs:1578) scans store.have().ids. A vaccine is is_ack so it is EXEMPT from the F-07 private-ingest limit (which only gates is_private, node.rs:3810). A forged/random-token vaccine matches nothing, is not added to immune, and falls through to store+reflood (node.rs:4202).
Fix
Add a store.seen(&id) short-circuit before the is_ack/vaccine handling so a duplicate vaccine is not re-scanned, and subject Vaccine bundles to a per-link rate limit (like F-07) since they are unsigned and freely mintable. Optionally cap the accepted vaccine hop_limit/lifetime in verify() so a forged anti-packet cannot self-assign a 255-hop, long-lived flood.

▸The self-declared 'A' is not backed by the code in the two surfaces that face the public first: docs, web, and the safety-net's own coverage claims

web self-declared A but the homepage hero sim (the 'you are running the real Hop protocol' claim) is OUTSIDE the docs-token-guard and carries 72 em/en dashes, a bare 'Bluetooth' label, and a REMOVED Wi-Fi Direct bearer presented as live (web-r2-01 confirmed). docs-drift is a genuine C: LICENSE.md is 0 bytes (confirmed), a phantom Multipeer bearer is 'building' in four docs, HOP_WIRE_VERSION is a phantom symbol, MECHANISMS.md still says wire=2. quality-net confirms the `minimal`/embedded C-ABI is NEVER compiled in CI (quality-net-r2-01, confirmed) and the Android hardware-key path has zero automated coverage while iOS got a test. The pattern: the mainline crypto/protocol is legitimately strong, but the claimed-A was measured against the happy path, not the public-facing copy, the un-exercised build configs, or the doc/legal surface a reviewer inspects first.

▸SQLCipher-at-rest is defeated in practice on Android - the single highest residual security risk, and it directly contradicts the headline F-25 claim

android-r2-01 (confirmed) and security-privacy-r2-02: messages.json / contacts.json / channels.json / media/* are written UNCONDITIONALLY in cleartext to filesDir in RELEASE builds, sitting next to the encrypted db. iOS correctly gated its equivalent behind #if DEBUG + completeFileProtection; Android did not. So the whole point of the hardware-key + SQLCipher work - encryption at rest - is bypassed on one of the two shipping platforms, in release. This is the clearest case of a headline remediation claim (F-25 'encrypted at rest') being false in the shipped artifact, and it's high-severity because it exposes full plaintext chat history + photos to any at-rest/backup/forensic access.

▸Deploy-gate and CI integrity leans on GitHub branch-protection that no repo file can enforce or verify - a single silent misconfiguration defeats the whole safety net

Recurring 'unknown' across infra, web, and quality-net: pages production deploy is NOT gated on CI green (infra-r2-01), require-ci trusts whatever check-runs happen to exist rather than a required-name allowlist (infra-r2-02) and treats all-skipped as green (infra-r2-08), and the entire deploy gate's integrity depends on branch protection that README documents as a manual step (quality-net-r2-03). Three independent auditors could not verify the live setting from the repo. Combined with the wire-v3 hard fork, this means a bad build or an incompatible wire bump can reach production without a real gate. The fix (a scheduled job asserting main's required checks match the CI job set) was proposed but not built.

▸Un-authenticated / un-rate-limited adversarial inputs recur across the protocol as a class the vaccine hardening only half-closed

core-protocol-r2-04: the private delivery-ACK (deliver_private Payload::Ack) is accepted on recognition alone with NO CDH proof - a forgeable delivery confirmation, the same attack class the vaccine path was hardened against, with no guarding test. security-privacy-r2-01/core-protocol-r2-03: forged unsigned Vaccine bundles are exempt from the private-ingest rate limit (is_ack), still store + reflood network-wide, AND now trigger an un-deduped O(held-bundles) scan per arrival. services-r2-03: endpoint rate-limiting trusts client-controllable X-Forwarded-For. The theme: the mainline authenticated paths are solid, but several ADVISORY/control paths (ACKs, vaccines, XFF, deep links) accept adversary-shaped input without proof or rate limit, and none of them has an adversarial test.

▸Exported, unconfirmed deep-links let a third party drive an authenticated send on both mobile platforms

android-r2-03: the exported BROWSABLE hopdemo://send deep link lets any app or web page drive an authenticated send on the victim identity with no confirmation. iOS gated its equivalent handleAutomationURL behind #if DEBUG (apple, correct), but the Android one is reachable in release. Cross-cutting because it's the same automation-seam that was legitimately useful for testkit but became a live attack surface on one platform. Low blast radius per message but it's an unauthenticated action-injection into a security product.

▸Real residual risk, ranked: the mesh is cryptographically sound on the happy path but not beta-safe operationally

Top residuals in burn-down order: (1) wire-v3 hard fork with no mixed-fleet/upgrade path = guaranteed cross-version delivery outage on any staged rollout (release-blocking, structurally missed). (2) Android plaintext-at-rest defeats SQLCipher in release (high, confirmed). (3) no crash telemetry + FFI panic-unwind gaps = field failures are invisible and can abort the process (blind beta). (4) 0-byte LICENSE = legally unshippable (trivial fix, hard blocker). (5) hardware-bound keys + no backup/restore = permanent identity + history loss on device change (data-loss UX). (6) vaccine/ACK/XFF unauthenticated-input DoS+forgery class. The crypto core, sender-spoof fix, prekey rotation, and store migrate-or-fail-safe genuinely hold under adversarial re-check - the risk has moved OUT of the protocol and INTO release engineering, operations, and the two non-mainline platforms/surfaces.

What no auditor owned

Structural gaps outside any subsystem - the distance to a credible beta.
UPGRADE / MIGRATION UNDER THE WIRE-v3 BUMP - the single biggest structural miss. bundle.rs:676 `is_supported_bundle_version(v) == (v == BUNDLE_VERSION)` means a wire-v3 node hard-rejects EVERY v2 bundle with UnsupportedVersion, and the vaccine id domain shifted to `v2`. There is no dual-decode window, no version-negotiation, no staged rollout gate. The MEMORY note already records this exact class of break for the relay fleet (old relay can't decode new-core apps). No auditor asked: what happens when a v2 phone in the field meets a v3 phone, or a not-yet-updated relay? A mixed fleet during any real rollout silently stops delivering across the version boundary. This is release-blocking and untested.
RELEASE / VERSIONING DISCIPLINE - every shippable surface is pinned at a zero-version with no bump policy: android versionCode=1/versionName 0.1.0, iOS MARKETING_VERSION 0.1.0/CURRENT_PROJECT_VERSION 1, HOP_ABI_VERSION frozen at 2 while wire went to 3, no CHANGELOG/RELEASE notes file, no git tags. The C ABI, the wire, and the app builds each version independently with no documented compatibility matrix tying them together. No auditor produced the (ABI v, wire v, app v, store schema v) compatibility grid a beta needs.
CRASH REPORTING / TELEMETRY / OBSERVABILITY ON DEVICE - there is a docs/crash-reporting-design.md but NO wired integration (no Crashlytics/Sentry/os_log signpost/Rust panic hook that reports off-device). The FFI catch_unwind gaps (core-ffi-sdk-r2-01) mean a panic in an un-wrapped path aborts with zero diagnostics reaching the developer. For a mesh app whose failures are field-only (BLE, background wake, securing-stuck), shipping a beta with no crash/anomaly telemetry means every field failure is invisible. The MEMORY files show the team already fights blind on device (0x8BADF00D watchdog, securing-stuck) - that is exactly what telemetry would surface.
STORE SUBMISSION READINESS - no auditor checked App Store / Play Store gating: iOS needs a privacy-manifest (PrivacyInfo.xcprivacy) and Always-location + BLE-background usage justifications (the app uses beacon-region wake and Always location per MEMORY); Android needs a Play-Console data-safety form and, critically, BLE-scan + background-location are policy-sensitive permissions that get apps rejected. android-r2-04 flags the app 'ships debug-shaped' (no minify/R8, allowBackup default) which is a submission blocker, but nobody assessed the store-policy surface itself.
BACKUP / RESTORE / DEVICE-MIGRATION of identity - keys are ThisDeviceOnly / StrongBox non-exportable (correct for secrecy) but that means a user who loses/replaces a phone loses their identity and all forward-secret history with NO recovery path. There is no documented account-recovery, identity-export, or multi-device story. security-privacy-r2-05 touches the Android legacy-seed migration but nobody assessed the user-facing consequence: hardware-bound keys + no backup = permanent identity loss on device change, which for a messaging product is a beta-blocking UX/data-loss gap.
MULTI-NODE SCALE - reviewed in the small only. The r2 findings repeatedly defer scale to 'another area' or 'fleet size': the fixed 16-bit mailbox prefix understates linkability below ~2^16 nodes (security-privacy-r2-03), the prefix-collision starvation probability (core-protocol-r2-01) is fleet-size dependent, the vaccine O(held) scan amplification (r2-03) scales with store size, and the backbone-429/wake-churn MEMORY note shows the relay already collapses under full-mesh load. No auditor ran or modeled a multi-node scale scenario; the discrete-event hop-sim explicitly does NOT exercise wire-v3 routing at scale (sim-wasm-r2-01).
LEGAL - LICENSE.md is 0 bytes (docs-drift-r2-01, confirmed) while Cargo.toml/README cite FSL-1.1-ALv2, so the project currently ships with NO license text: legally unshippable as-is. Beyond that: no per-package LICENSE for the independently-publishable Swift/Kotlin/bearer packages, no third-party dependency license inventory / attribution file (deny.toml exists for advisories but no NOTICE), no privacy policy or ToS for a messaging product handling user content. Nobody produced the legal-readiness checklist a public beta requires.
OPS RUNBOOKS / INCIDENT RESPONSE - the fleet is currently torn down (relays_enabled=false per MEMORY) and the re-enable is a one-line flip, but there is no runbook for: turning the fleet back on, rolling forward through a wire bump without a mixed-fleet outage, rotating the relay identity/cert, responding to the vaccine-amplification DoS (security-privacy-r2-01), or the 429/wake-churn overload the MEMORY already documents. infra README first-deploy docs are stale (reference retired Spacelift, infra-r2-05/06). No on-call/alert story: monitoring APIs aren't even enabled in apis.tf (infra-r2-04) and alert_email is dormant.
SUPPLY-CHAIN - partially covered (deny.toml, SRI on sim third-party JS) but with holes nobody closed as a theme: the fontawesome kit and Google Fonts are unpinned external loads (web-r2-04), the esp32/ESP-IDF component pulls and the wasm-bindgen/maplibre/deck.gl chain have no lockfile-integrity gate in CI beyond SRI, no SBOM is generated for any shipped artifact, and the build SA still carries projectIamAdmin (infra honest-residual). No cargo-vet / dependency-provenance policy.
BATTERY / THERMAL / DATA on device - a BLE dual-role always-scanning + background-wake + relay-websocket-keepalive mesh app is inherently a battery and cellular-data consumer, and iOS/Android will kill or throttle it (the MEMORY already shows cpu_resource kills and watchdog). No auditor measured or even estimated battery draw, background-CPU budget, or metered-data behavior. For a beta on real phones this is a top user-facing risk and it was structurally skipped.
ACCESSIBILITY & LOCALIZATION - zero coverage of VoiceOver/TalkBack labels, Dynamic Type, contrast in the actual apps (the web light/dark got attention but the apps did not), and everything is English-only with no i18n scaffolding. Lower priority than the above but genuinely untouched.
DATA-LOSS / DURABILITY EDGE CASES aggregated across areas but never owned the Firestore TTL re-anchor can sweep a live bundle early (stores-r2-01), the plaintext->SQLCipher migration leaves stale WAL sidecars (stores-r2-02), completeFileProtection can silently drop a locked-screen receive from the iOS UI mirror (apple-r2-03), and the seen-cap eviction is non-transactional (stores-r2-04). Individually low/medium; as a class, 'can we lose or early-expire a delivered message' has no cross-cutting owner or end-to-end durability test.

Roadmap from here to beta

Dependency-ordered, not time-boxed. Legal + release-blockers first, then the confirmed security holes, then the wire-v3 upgrade path.
Phase 1

Legal + release-blockers: make it lawful and versioned to ship at all

These are cheap, hard blockers: a 0-byte license is legally unshippable, un-versioned artifacts make every later phase un-trackable, a broken feature build blocks the embedded story, and code-contradicting security docs erode trust for reviewers. All are independent of each other and gate everything downstream, so they go first and burn the highest-certainty risk for the least work.

  • Populate LICENSE.md with FSL-1.1-ALv2 text and add per-package LICENSE files to the publishable Swift/Kotlin/bearer packages (docs-drift-r2-01); add a NOTICE/attribution file and a privacy policy stub for the messaging product
  • Establish a version-and-compatibility policy: bump android versionCode/versionName + iOS MARKETING_VERSION off 0.1.0, add a CHANGELOG, and write the (ABI v, wire v, store-schema v, app v) compatibility matrix as a checked-in doc
  • Fix `cargo build -p hop --no-default-features` (core-ffi-sdk-r2-02) so the minimal/embedded path compiles or fails with a clear compile_error!, and correct the impossible Cargo.toml build command (r2-04)
  • Reconcile the doc/code contradictions the remediation created: SECURITY.md accepted-risks vs shipped hardware-keys+rotation (docs-drift-r2-02), MECHANISMS.md wire=2->v3 + token-only vaccine (r2-04), phantom HOP_WIRE_VERSION->BUNDLE_VERSION (r2-05), phantom Multipeer bearer (r2-03)
Phase 2

Close the confirmed at-rest + action-injection security holes on the shipping platforms

These are confirmed, release-reachable security defects that directly falsify the headline 'encrypted at rest' claim and expose an unauthenticated send. They depend on nothing from later phases and represent the highest real user-facing risk after the legal blockers, so they burn down before any feature or scale work.

  • Stop writing plaintext messages.json/contacts.json/channels.json/media to Android filesDir in release: gate behind DEBUG/HOP_AUTO or persist inside SQLCipher/EncryptedFile, and rebuild UI history from the node store (android-r2-01 / security-privacy-r2-02, the confirmed high)
  • Switch iOS UI-mirror JSON to completeFileProtectionUntilFirstUnlock or rebuild from the node store so a locked-screen background receive is never dropped (apple-r2-03)
  • Gate or remove the exported BROWSABLE hopdemo://send deep link outside debug builds on Android (android-r2-03); confirm iOS parity
  • Remove or lock down the dead legacy relay path so it cannot reintroduce relay split-brain (apple-r2-01); make Android relaysEnabled a single source of truth across both init paths (android-r2-02)
  • Add a hardened Android release buildType (minify/R8, allowBackup=false, strip HOPLOG address/text logging) (android-r2-04/05)
Phase 3

Wire-v3 upgrade path + rollout gating: don't split the fleet

The wire-v3 hard fork is the single biggest structurally-missed, release-blocking risk: any staged rollout of the current build silently stops delivering across the version boundary, and the fleet re-enable would expose it. It depends on the versioning policy from Phase 1 and must precede any production traffic, so it's the gating phase for going live. The deploy-gate hardening lives here because it's the backstop that prevents an incompatible build from reaching the fleet.

  • Design and implement a mixed-fleet decode window: accept v2 AND v3 in is_supported_bundle_version behind a staged-rollout flag, or ship an explicit version-negotiation/hop-limited bridge, with a test that a v2 and a v3 node still deliver across the boundary
  • Add a hop-sim / integration scenario proving cross-version delivery during a rollout, plus the wire-v3 k-bit prefix / anonymity-set routing at scale (sim-wasm-r2-01)
  • Harden the CI deploy gate before any fleet re-enable: gate pages deploy on CI green (infra-r2-01), add a required-check-name allowlist (infra-r2-02/08), and add a scheduled job asserting main's branch-protection required checks match the CI job set (quality-net-r2-03)
  • Sequence the relay-fleet re-enable (relays_enabled) only AFTER the mixed-fleet path lands, and set HOP_NO_RELAY=1 on the example endpoint until then so it stops dialing the dead relay (services-r2-01)
Phase 4

Observability + operability: stop flying blind on device and in the fleet

A beta on real phones with no crash telemetry and no fleet monitoring means every field failure (BLE, securing-stuck, watchdog kills already in MEMORY) is invisible and un-actionable. This depends on the app builds being release-shaped (Phase 2) and the fleet being about to carry real traffic (Phase 3). It converts the remaining field risk from invisible to observable before real users arrive.

  • Wire real crash reporting on both apps (per docs/crash-reporting-design.md) and a Rust panic hook that reports off-device; wrap ALL node-calling hop_* ABI fns in catch so no path unwinds across extern "C" (core-ffi-sdk-r2-01)
  • Enable monitoring.googleapis.com + logging.googleapis.com in apis.tf and depends_on the observability resources; activate alert_email (infra-r2-04)
  • Write ops runbooks: fleet re-enable, wire-bump rollout without outage, relay identity/cert rotation, and the 429/wake-churn + vaccine-amplification overload responses; fix stale infra README/tfvars.example (infra-r2-03/05/06/09)
  • Measure battery/background-CPU/metered-data on a real device soak and set budgets; fix the soak doc 6-device drift (quality-net-r2-04)
Phase 5

Protocol robustness + adversarial-input hardening + coverage asymmetry

These are the medium/low residuals that a security-sensitive beta should not carry but that don't block the mainline happy path: forgeable ACKs, un-rate-limited vaccine DoS, prefix starvation, and the never-compiled build configs. They depend on the wire path being stable (Phase 3) and are best done once telemetry (Phase 4) exists to observe their effect. Ordered after the confirmed criticals because each is lower-probability or lower-blast-radius.

  • Add CDH (recipient-only) authentication to the private delivery-ACK path or make the bare private Ack advisory-only, with a forgery test (core-protocol-r2-04)
  • Rate-limit and seen-dedup unsigned Vaccine bundles before resolve_vaccine_target runs so a forged-vaccine flood can't force repeated full store scans or network-wide reflood (core-protocol-r2-03 / security-privacy-r2-01)
  • Add the epidemic/spool fallback + colliding-recipient test for prefix-bucket starvation (core-protocol-r2-01); pin Payload/StreamKind discriminants with a test (r2-05)
  • Close CI coverage asymmetry: compile the minimal feature + a real embedded-target cargo check in CI (quality-net-r2-01), add automated Android KeystoreSecret coverage to match the iOS test (quality-net-r2-02), run the esp32 host demo build
  • Fix the store durability edge cases as a set: Firestore TTL re-anchor (stores-r2-01), stale WAL sidecars in migration (stores-r2-02), unclamped rehydrate seen-window (stores-r2-03), non-transactional seen-cap eviction (stores-r2-04)
Phase 6

Beta-readiness polish: backup/recovery, store submission, public-copy honesty, scale, supply-chain

Final burn-down for a credible public beta: recovery/backup and store-policy are user-facing beta blockers but depend on the security and versioning foundation being set; public-copy honesty and scale/supply-chain are the last polish that makes the product defensible to an outside reviewer and app-store reviewer. Ordered last because none of it gates internal correctness, but all of it gates an outside-facing beta.

  • Design an identity backup/restore or explicit multi-device story so hardware-bound keys don't mean permanent identity+history loss on device change; re-key legacy Android installs off the ANDROID_ID-derived secret (security-privacy-r2-05)
  • Store-submission readiness: iOS PrivacyInfo.xcprivacy + Always-location/BLE-background justifications, Android Play data-safety form + BLE-scan/background-location policy review
  • Bring sim/ under docs-token-guard and rewrite its 72 dashes, bare 'Bluetooth' label, and removed Wi-Fi Direct bearer so the homepage hero matches the shipped product (web-r2-01/02/03); self-host or SRI-pin Google Fonts + fontawesome (web-r2-04); origin-validate the sim postMessage (web-r2-05)
  • Model multi-node scale: adaptive-k or documented stance for sub-2^16-node mailbox linkability (security-privacy-r2-03), prefix-grinding Sybil eviction hardening (r2-04), and a seeded scale stress test
  • Supply-chain: generate an SBOM per shipped artifact, add cargo-vet/lockfile-integrity to CI, and narrow the build SA's residual projectIamAdmin
  • Fix the fixed 16-bit prefix mailbox-tag exposure decision (core-protocol-r2-02) and untrack ble-lab/android/local.properties (quality-net-r2-05); resolve esp32 dual main.c (r2-06)
