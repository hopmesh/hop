Where

Detail

04

Completeness critique

The critic's read on whether the closures held and what is still open.

1. Did the closures hold, or did any regress?

Mostly held, with one genuine live regression and a cluster of false/latent closures on the platform layers.

Clean holds (verified end-to-end): C-ABI deferred-send-rides-the-ratchet; Stores seen_expiry (full chain memory/sqlite/firestore/wasm + both JS bridges + revert-meaningful test); Apple LAN dedup-before-surface (both onUp and onClose halves, plus the BLE mirror); endpoint 64 KiB head cap (unit + real-socket 431 test); relay ingested-set bound (unbounded set to age-evicted map); Kotlin base58 over/under-length require; infra smoke + crash-loop alert + secret pin; CI LICENSE/guard + testkit send-settle + iOS-fallback logging; Android DNSSEC concurrency bound + GATT error context. Ground truth backs this: all four suites green (Rust 333, Apple 56, JVM 44, WASM 2.9M checks + 15 scenarios), guards pass, cbindgen byte-identical, ABI=2 consistent.

The one real regression, call it out explicitly (relay closure #2, services/hop-relayd/src/main.rs, both isNew=true, both high):

• Healthz no longer budget-exempt (the strongest finding). Every inbound WS now hits admit_conn() at line 529 before classification, so a GET /healthz is shed once mesh links hit MAX_CONNS=1024. This fires organically, no attacker: a healthy relay at capacity fails its Cloud Run health check, restarts, drops the whole mesh, and triggers a thundering reconnect. Pre-#39 healthz classified first and was never gated. This is the only place a pass-4 fix shipped into a live binary and made a running path worse.

• Slowloris now camps a mesh slot for the full 5s peek. Lateral trade (pre-#39 the inline peek serially stalled the accept loop, arguably equal-or-worse), but it composes with the healthz shed into the restart-loop path.

False or latent closures (green suite masks them):

• Apple driver flagship NOT-HELD: the new hpsRegister(...then:) async overload is dead code; the Create button (ContentView.swift:919) still binds the sync overload and still core.syncs on main. Behavior is byte-identical, so not a regression, but the claimed fix did not land.

• Android teardown() is dead code (zero callers) and would crash (RejectedExecutionException from OkHttp callbacks onto a shut-down executor) and brick the singleton (never nulls inst) if wired. RelayBearer is also non-restartable after stop, refuting the commit's own "a second start gets a fresh one" claim.

• Kotlin HopMessage encapsulation overstated: from/body are still public mutable ByteArray; the "fix" is docs + opt-in *Copy(), plus a newly introduced content-hashCode-over-mutable-field HashMap footgun.

• Infra silent-region alert will false-page every scale-to-zero region the moment relays_enabled flips true.

• WASM seenExpiry: committed sim/pkg blob is stale, but CI/pages regenerate before publish, so the live deploy is not stale (auditor overstated this one).

2. Grades that look too generous

• Relay service C+/D is the clearest over-grade. Two high isNew regressions on the one shipped-live binary; the closure that was supposed to be neutral introduced an organic availability failure. Should read C or C-.

• Apple driver + demo C+/F: the headline closure is dead code and nothing tests the changed surface. F coverage is honest; C+ quality credits a fix that never runs.

• Android driver C/F: teardown never executes, plus a new silent host:port rejection against a documented/advertised UI form. Generous.

• Kotlin SDK B-/F: encapsulation claim didn't hold, the one trivially-testable fix (base58 length) has no test, and a new HashMap footgun landed. B- overstates a wrapper whose flagship claim is docs-only.

Endpoint/Gateway B-/C and Infra B are defensible (the unguarded gateway is a pre-existing gap the fix didn't reach, not a new regression; 3 of 4 infra closures held cleanly).

3. Single most important thing still open

Two answers, kept distinct on purpose:

• Most urgent to fix: the relay healthz-shed-at-cap regression. It is live, organic, and self-inflicted, and it is the only defect that bites a running production system with no attacker and no latent-code caveat.

• Most important structural open item (of the three you named): the platform-layer test coverage gap, specifically Android bearer-ble/bearer-lan (0 JVM tests) and Kotlin JNA marshalling (0 tests, base58 length is trivially JVM-testable and still unverified). This is the root enabler: the dead-code teardown, the dead async overload, the non-restartable bearer, and the crash-on-stop all shipped green precisely because nothing exercises the changed surface. Apple's ~9% (onUp/onClose tested via a parallel re-implementation, never the real object) is the same disease, one platform over. Fix this and the false-closure pattern stops repeating.

4. Net vs pass 4

Modestly better overall, materially better on the tested Rust core, but net worse on the one live-shipped service (relay), with a pile of latent platform debt the green suite hides.

The gains are real and concentrated where tests exist: core and wire/crypto are untouched and still A/A-, and the store/C-ABI/endpoint/CI/base58/infra closures genuinely held. The losses are concentrated where tests don't exist: the relay picked up two high live regressions, and the Apple/Android/Kotlin layers accumulated false-closure debt (dead code, latent crashes, overstated encapsulation) that passes green only because nothing tests it. This is exactly the coverage-posture split from the record: well-tested Rust improving, untested platform edges degrading. Until the relay regression is fixed, "better" is not unambiguous, and "all green" overstates the health of everything below the Rust line.

Priority-ordered next actions

1. Exempt healthz and classify before charging a mesh slot in admit_and_serve_ws so a full relay stops failing its own health check and restart-looping the mesh (services/hop-relayd/src/main.rs ~529).
