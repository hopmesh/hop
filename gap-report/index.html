The feature work was real and coherent. The risk clusters along three axes the velocity outran.

AXIS 01

No net under the wire or the deploy

Push-to-main auto-applies ~42 relay regions with zero tests. The versioned wire format has a version byte nothing reads. That already bricked the relay once.

AXIS 02

The §39 promise has holes

The receiver-beacon gradient can be hijacked by any participant, and the mailbox tag is a public, never-rotating hash of an openly-flooded key. Design says otherwise.

AXIS 03

Recovery got dropped in the cutover

Shared bearers lost the Bluetooth and LAN self-heal; the persistence layer silently discards any record whose layout changed, and already ate the send queue once.

SEVERITY High Medium Low Verified clean STATUS Fixed

Remediation update: all three axes closed, then the partials and deferrals too

Axis 1 (no safety net): CI now gates every push (tests + clippy + contract-purity + header-drift), the wire format has a real version gate with golden tests (bumped to v2), and rehydrate() counts what it drops instead of silently eating the queue. Axis 2 (§39 holes): the receiver-beacon is bound to its owner so it can't be hijacked, and the mailbox tag now rotates per epoch (decoupled from the prekey). Axis 3 (dropped recovery): Bluetooth off/on, LAN dial-timeout, and BLE advertiser self-heal are all restored on both platforms.

Each finding card and ledger row below shows its resolution. All 60 findings addressed & verified · the four former partials are now fully closed (SQLCipher-at-rest keyed through the SDK, the beacon UUID single-sourced across platforms, per-source endpoint rate limiting, the Android manifest cleanup) · every documented deferral was picked up on a second pass (k-bit removal, wrapper parity, schema guard, session GC, DNSSEC Ed25519 + RSA floor, crash logging). Terraform is written but not applied; nothing pushed or deployed yet.

§ 01 / 07 CI · Wire format · Persistence

No net under the wire, or the deploy

The single highest-leverage cluster: nothing catches a bad commit before it reaches all regions, and the wire format has no version gate. Fix this first, because it protects every change after it.

HighF-01CI / DeployFixed

Zero CI for code, and push-to-main auto-deploys the fleet ungated

The only GitHub workflow is the site build. The Cloud Build trigger fires on every push to main with no path filter and runs build, push, and tofu apply -auto-approve, with no cargo test, clippy, contract-purity check, or smoke step. The purity guardrail you added on purpose has zero callers. A commit that compiles but regresses behavior or the wire format rolls to all regions, with a human curling the relay as the only detector.

EVIDENCEinfra/cloudbuild_trigger.tf:76 (trigger on ^main$, no filter) · tools/codegen/check-contract-purity.sh (0 callers) · cargo test --workspace = 169 green locally
FixedAdded .github/workflows/ci.yml (cargo test + clippy -D warnings + contract-purity + cbindgen header-drift) on every push, and fixed all pre-existing clippy warnings so the gate is green today.
HighF-02Wire formatFixed

BUNDLE_VERSION is written but never read, and there are no golden vectors

Every bundle stamps a version byte that nothing checks on decode. Removing Destination::InternetEgress shifted the postcard variant indices (the commit message itself warns "full fleet + relay must rebuild"), which is exactly what left the deployed relay unable to decode new traffic. Ingest drops undecodable frames silently. No cross-version decode fixtures exist anywhere; the version field on adverts has the same write-only pattern.

EVIDENCEbundle.rs:23 stamped, never read · bundle.rs:540 bare postcard decode · commit 5dd64d3 (index shift) · node.rs:2788 silent drop
FixedBundle::from_bytes AND Bundle::verify (the network hot path) plus Advert::verify now reject unknown versions with Error::UnsupportedVersion; a golden test locks the Destination discriminants and append-only discipline is documented.
HighF-03PersistenceFixed

rehydrate() silently discards any persisted struct whose layout changed

Every persisted blob is decoded with a bare if let Ok(...) and dropped on error with no log or counter. postcard is positional and carries no version tag, so any field add, remove, or reorder silently vanishes the state on upgrade. Not hypothetical: the §39 P3 commit appended a field to PendingContent mid-fleet, so any in-place upgrade with queued sends lost the whole queue. The next field added to PeerSession silently wipes every ratchet session on upgrade, reproducing the "Securing forever" class with zero telemetry.

EVIDENCEnode.rs:713-772 (silent drop on Err) · commit 6bb5739 (PendingContent gained `private`) · postcard pinned in Cargo.toml:30
FixedNode::rehydrate now counts undecodable persisted records (RehydrateReport), drained by take_rehydrate_report and logged by the host on open. +2 tests.
MediumF-04PersistenceFixed

Persisted bundles cross wire-format changes unguarded on disk

The bundles table stores raw postcard bytes. Two incompatible layout changes shipped in the deployed window with the version unbumped and unread. After an in-place upgrade, previously-persisted bundles fail to decode, so the device's own undelivered messages silently stop retransmitting. The on-device impact of the June 29 shift was masked only by the same-day app-id rename handing everything fresh data dirs, which will not repeat.

EVIDENCE56982da inserted `private` mid-struct · 5dd64d3 shifted Destination · hop-store-sqlite/src/lib.rs:88-97 returns None on decode fail
FixedOn-disk bundle decode runs through the same version guard, so a breaking layout change fails loudly instead of silently dropping the queue.
§ 02 / 07 Untraceable messaging · Crypto

The untraceable path has holes

§39 is the flagship promise. Two gaps sit between what DESIGN.md guarantees and what the code enforces. Neither breaks confidentiality; both break the anonymity and availability the design claims in present tense.

HighF-05§39 · flagshipFixed

Receiver-beacon gradient can be hijacked or black-holed

DESIGN.md states "only the holder of M can advertise a gradient for M; no node can hijack or black-hole a prefix it doesn't own." The code enforces neither. The beacon carries no signed-prekey binding and is signed by the node's identity key, not the prekey the design assumes. Since the mailbox tag is a public hash of the openly-flooded prekey, any participant can publish a beacon for a victim's mailbox with a high sequence number. The node installs it, supersedes the legitimate gradient, and then routes every private bundle for that mailbox only down the attacker's link. The forged mailbox also drains the victim's cloud spool toward the attacker. Content stays sealed, so this is denial and capture, not decryption, which is why it is High and not Critical.

EVIDENCEDESIGN.md:2386-2387, 2466 (the invariant) · discover.rs:89,164-174 (no SPK, identity-signed only) · node.rs:3491-3498 (routes only to the beacon link) · hop-relayd/src/main.rs:1004-1030 (spool drain)
FixedA gradient now installs only if the mailbox matches the publisher's own signed identity (address+epoch, see F-06) , the relay recomputes it from the beacon's signed address, so a non-owner can't forge it. Rejection test added.
HighF-06§39 · linkabilityFixed

The mailbox tag is publicly linkable to identity and never rotates

The tag is a deterministic BLAKE3 hash of the recipient's signed-prekey public, which floods in cleartext in an advert whose publisher field is the node's address. Any relay or global observer can compute the hash for every known address and build a full tag-to-address table. Worse, the P4 beacon rides a body whose cleartext publisher is the address, so it announces "address A owns mailbox M" verbatim, and this is the default. Prekey derivation takes no epoch input, so the "rotatable pseudonym" never rotates. This deanonymizes the gradient, the blind spool, and the private delivery-ACK. DESIGN.md asserts in present tense that tags rotate per prekey epoch; they do not.

EVIDENCEcrypto.rs:342-344 (tag = H(spk_pub)) · discover.rs:71,100 (prekey floods cleartext) · node.rs:1205-1220,638 (beacon publishes address, default on) · crypto.rs:105-115 (no epoch input) · DESIGN.md:2465 (false claim)
FixedRederived the mailbox as H("v2"‖address‖epoch) with a daily epoch + recent-epoch beacon window, decoupled from the (deterministic) prekey. Bumped the wire version to 2. Rotation + window tests.
MediumF-07§39 · abuseFixed

Private bundles are unauthenticated with no ingest rate limit or dedup cap

A private bundle sets an empty signature and passes verification for any sealed bytes whose id matches the payload hash, so any node can mint unlimited valid private broadcasts. There is no per-link ingest rate limit, and the seen-dedup table is pruned only by an attacker-set lifetime (up to ~50 days) with no row cap and no delete on eviction, so it bloats for weeks. Relayed bodies and the gradient table are capped, so amplification is bounded; the unmitigated sinks are the seen table and the unclamped lifetime, and the surface reaches the internet-facing relay and paid Firestore.

EVIDENCEbundle.rs:434,460-469 (empty sig, id-only verify) · hop-store-sqlite/src/lib.rs:51,72-105 (no cap, lifetime-only prune) · DESIGN.md:2464-2468 names caps as the day-one control
FixedClamped the sqlite seen window to 7d, capped the table at 200k rows, and added a per-link rate limit for unsigned private bundles. +test.
LowF-08CryptoFixed

Key material is never zeroized in the core

No struct uses zeroize, so the identity seed, prekey secrets, X3DH roots returned by value, and every retired prekey secret retained forever sit in heap and stack until overwritten. The dalek crates wipe their own copies, but every core-owned copy does not. Threat model is local memory disclosure (core dump, swap, post-compromise), hence Low, but retaining retired prekey secrets unwiped borders the forward-secrecy policy.

EVIDENCEcrypto.rs:44-46,171-177,248,268 · node.rs:436 (spk_secrets retained) · grep for zeroize = 0
FixedZeroize the prekey secret on drop and wrap the retained spk_secrets in Zeroizing.
§ 03 / 07 Bearers · Core congestion · Apps

Where delivery breaks on real hardware

The bearer cutover silently dropped recovery behavior the legacy paths had, and the core still serializes bulk work behind the one lock that Noise handshakes need. This is where "it works in the lab, not on the fleet" shows up.

HighF-09CoreFixed

One Mutex<Node> plus a per-inbound full-store rescan keeps "Securing forever" live

The whole node sits behind a single lock that every entry point takes. WAL and an O(N) precompute landed, but the offer path still does a full-store scan on every accepted relayed bundle, every new beacon, and every link-up. The in-code comment names this exact read-storm as what starved Noise handshakes and made messages hang. The store is bounded to ~128 bundles so the constant shrank, but a burst still costs a scan under the one lock handshakes need, and §39 added more offer triggers.

EVIDENCEcore/hop/src/lib.rs:392,454-465 (single mutex, all entry points) · node.rs:3451-3477,3462-3465 (full scan + the comment) · triggered at node.rs:3243,3411
FixedExtracted offer_one_to_link + offer_bundle_to_all_except, so a just-arrived bundle is offered on its own instead of rescanning the whole store under the lock.
HighF-10Bearer · AndroidFixed

The Android production path lost Bluetooth off/on recovery

Shared bearers default on, but the documented adapter-state receiver lives only in the dead legacy branch. The shared BleBearer has zero adapter-state handling: its L2CAP accept thread breaks on IOException and is never restarted, and nothing re-opens the GATT server, advertiser, or scanner after the radio comes back. A Bluetooth toggle (airplane mode, battery saver, or the very recovery the comments recommend) leaves the device permanently deaf on BLE until force-stop. If BT is off at launch the unguarded L2CAP open throws through an unisolated startup loop and can abort LAN and relay too.

EVIDENCEHopConfig.kt:25 (shared default) · HopBearer.kt:323 (receiver in legacy branch only) · BleBearer.kt:310,314-325 (unguarded open, accept breaks) · grep ACTION_STATE_CHANGED in bearers/android = 0
FixedThe shared Android BleBearer now watches ACTION_STATE_CHANGED (tear down / bring back up), guards the L2CAP open, and restarts the accept loop; BearerManager isolates each bearer's start/stop.
HighF-11Bearer · AppleFixed

The Apple LAN bearer has no dial timeout and never recovers the listener

The link arms its no-HELLO reaper and liveness timers only after reaching ready, and ignores the waiting state that a connection sits in on refused or unreachable. A wedged dial self-retains forever and pins the peer's id in the dialing set forever, permanently blacklisting that peer for the process, and the greater-id tiebreaker means it will not dial back. Separately, the listener and browser only log on failure with no restart, so after a Wi-Fi transition or sleep the device silently stops accepting and discovering on LAN. Android's LAN dial has a 5s timeout; this is Apple-specific.

EVIDENCELanBearer.swift:71-98 (reaper on ready, ignores waiting) · swift:81,263-270 (self-retain, dialing pin) · swift:236,258 (log-only on failed)
FixedLanLink arms its connect deadline from start() and handles .waiting; the NWListener/NWBrowser restart on failure with backoff.
MediumF-12Bearer · BLEFixed

Shared BLE bearers dropped the advertiser self-heal on both platforms

The spec requires a periodic self-heal tick to re-arm a wedged advertiser; the legacy call is gated off on the default path. The shared Android advertiser is only re-armed on service-added, never periodically, and stop clears the set with no re-arm. On Apple, an L2CAP-publish or advertising-start error just logs and returns (undiscoverable, no retry), and the state-restoration hook is a no-op whose own comment cites the requirement it skips. Android also never shuts its beacon scheduler down on stop, so the iBeacon advertiser restarts after the bearer is stopped.

EVIDENCEble-lab/SPEC.md:227,409 · BleBearer.kt:348,388-401 (only on serviceAdded) · swift:322-323,335-337,362-365 (log-only, no-op restore)
FixedPeriodic advertiser self-heal on both platforms (re-arm L2CAP / advertising / beacon); Android Peripheral.stop() now shuts down beaconSched.
MediumF-13Bearer · RelayFixed

Relay reconnect policy invites synchronized storms

Both relay bearers reset backoff to the 1s minimum on socket-open rather than after proven stability, so a relay that accepts then immediately drops (the observed overloaded, scale-capped regime) is re-dialed every second forever. Android adds no jitter while Apple adds up to a second, so an Android sub-fleet reconnects in lockstep, and every push-to-main redeploy drops all fleet sockets at once. Neither inspects the upgrade status, so a 429 with Retry-After is treated as any other failure.

EVIDENCERelayBearer.swift:144 · RelayBearer.kt:101,115-117,128-133 (reset on open, no jitter, Response discarded)
FixedBoth relay bearers reset backoff only after a stable window, add jitter (Android had none), and honor a 429 Retry-After.
MediumF-14Bearer · LANFixed

LAN discovery is one-shot, so a transient failure loses the peer for the session

Dials fire only on discovery-change events. A resolve failure (the common busy error) or a failed connect just removes the peer from the dialing set and returns with no retry, and lost is empty so there is no lost-then-found churn to recover. With Wi-Fi Direct removed, LAN is the only Wi-Fi transport for Android-to-Android, so one transient failure during startup or doze permanently forfeits the high-bandwidth path, leaving BLE as the only fallback. The BLE central re-dials on every advert; LAN lacks that pressure.

EVIDENCEbearer-lan/LanBearer.kt:331-334,350-357,294 · Apple mirror at LanBearer.swift:245-257
FixedBoth platforms remember discovered peers and periodically re-dial any known-but-unlinked one, instead of forfeiting it until mDNS re-announces.
MediumF-15App · bothFixed

Optimistic send has no failure state

The bubble is inserted with a null id and patched later. If the core send throws (a store or seal error), the stamp rewrites the id to null, failed is never set, delivery tracking skips the row, and the message silently never sends. The retry affordance is gated on the failed flag, so it never engages; the only writer of failed is a manual queue clear. The common "peer unreachable" case correctly defers rather than throwing, so this fires on real store and seal errors: rare, but silent loss with the error swallowed.

EVIDENCEAndroid HopBearer.kt:504-518,1475, retry gate MainActivity.kt:764-772 · iOS HopBearer.swift:690-702 · throws from core/hop/src/lib.rs:489-504
FixedA thrown core send now marks the bubble failed on both apps, so the existing "Not sent · tap to retry" affordance engages.
§ 04 / 07 Services · Infra · Observability

The cloud sees more than it should, and less than it needs

The ~42-region relay fleet mirrors delivery metadata into durable logging, has no health probe or alerting, and runs the P5 spool worker with no tests. The most sensitive dataset in the system is the least watched over.

HighF-16Infra · privacyFixed

Relay netlog mirrors delivery metadata into Cloud Logging with 30-day retention

Every netlog line is echoed to stderr explicitly so it lands in Cloud Logging. Those lines include device-address prefixes on connect and leave, ingest and handoff destinations with region, spool mailbox-tag prefixes, and want-beacon pulls. Each region is its own Cloud Run service, so logging region-tags and timestamps every line, exactly the "pseudonymous address to coarse location and activity timeline" the design names as the most sensitive dataset and claims is ephemeral or on-device only. Infra defines no retention override or exclusion, so it persists in the default bucket for 30 days.

EVIDENCEmain.rs:94-98 (unconditional stderr mirror) · main.rs:411-416,385,966-971,992-996,1019-1023 · DESIGN.md:1748-1756 · grep logging retention in infra = none
FixedRoute relay logs to a 3-day bucket and exclude them from the 30-day _Default (observability.tf). Written, not applied.
HighF-17Infra · livenessFixed

No liveness probe, and the only health signal is the public stream slated for removal

The log stream and the Firestore heartbeat run on their own threads, independent of the driver loop. If the driver deadlocks, TCP accepts and the stream keep working, the heartbeat keeps advertising the node as warm, and with one instance per region a wedged instance is the region. Cloud Run defines no startup or liveness probe, so its default TCP check passes for a wedged instance and never restarts it. There is no health endpoint or metrics. This creates an ordering constraint: a health replacement must land before the public stream can be removed, or the fleet goes blind.

EVIDENCEmain.rs:132-168,366-441,801-806 · cloud_run.tf:21-98 (no probes) · DESIGN.md:1436 forbids external region probing
Fixedhop-relayd serves a real /healthz backed by a driver-loop heartbeat, wired as Cloud Run startup + liveness probes.
HighF-18TestsFixed

The P5 spool / want-beacon worker has zero tests; cross-region pull is untested anywhere

The ~1,000-line production handoff worker implementing blind spool and want-beacon pull has no test functions; the one integration test covers only WS framing. The core-level test exercises a single in-memory relay node, and the relay lib tests contain no spool coverage. So the cross-region spool, beacon, pull path, arguably the dominant real-world offline-delivery path in a 42-region fleet and the mechanism that resolved the default-relay regression, has no automated coverage at any layer, and prior fleet verification never exercised it either.

EVIDENCEservices/hop-relayd/src/main.rs (0 tests, spool/wanted at 436-437, 100k clear at 915-924) · core-level single-node test at node.rs:4477
FixedExtracted the spool/want-beacon worker behind a MailboxStore trait and added a two-region test proving exactly-once cross-region pull. CI runs the firestore-feature tests.
MediumF-19Infra · endpointFixed

The internet-facing hop-endpoint has no abuse controls and unbounded thread spawning

The always-on public endpoint parses untrusted request bundles and reverse-proxies plain HTTP with no per-source rate limiting, dedup, concurrency cap, or panic isolation. The accept loop spawns one OS thread per connection and per request, and established sockets loop forever, so many connections exhaust the single 512Mi instance. The orphaned hop-gateway crate implements exactly these controls (rate limit, dedup, size caps, tests) as dead code. The driver runs on the main thread so a panic restarts cleanly and the single instance bounds cost, which is why this is Medium-priority hardening.

EVIDENCEservices/hop-endpoint/src/main.rs:133-136,284 (thread per conn / req) · grep rate/limit/semaphore/dedup = none · controls exist unused in hop-gateway
FixedBounded concurrent connections (MAX_CONNS + guard) and catch_unwind panic isolation, PLUS a per-source sliding-window rate limiter (allow_source: 100 req / 10s per IP, swept map) that drops the connection before any work. Thread-exhaustion, panic, and single-IP flood are all bounded now.
MediumF-20Infra · privacyFixed

The Firestore presence collection is a permanent per-device location log

Presence docs map a device's address to its last-seen region and heartbeat, written on every check-in, with no expireAt and no TTL policy, and remove never touches them. So the cloud keeps an indefinitely-retained, queryable per-address to region timeline forever, the dataset the design calls the most sensitive and claims is storage-limited by design. The staleness filter is only a 90-second read-side filter, not deletion. The registry docs have the same gap.

EVIDENCEmain.rs:929-937 · hop-store-firestore/src/lib.rs:662-670 (no expireAt) · infra/firestore.tf (TTL only on bundles) · DESIGN.md:1755-1767
FixedPresence + registry docs now stamp expireAt, with google_firestore_field TTL on both collections (read path already ignores stale presence).
MediumF-21Infra · durabilityFixed

The durable mailbox can drop last-moment bundles on scale-to-zero

The Firestore store accepts bundles into memory and mirrors them from a background thread over an unbounded channel, best-effort so the hot path never blocks, while the module doc sells it as the durable mailbox that survives scale-to-zero. The fleet runs min-instances zero with idle CPU throttling and relayd has no shutdown handler, so when the last socket drops, pending mirrors and the periodic spool writes die with the reaped process. A private bundle accepted moments before its sender disconnects can vanish, reopening the offline-delivery regression class the design rests on.

EVIDENCEhop-store-firestore/src/lib.rs:3-4,59-75 · cloud_run.tf:26,84 (min 0, cpu_idle) · grep SIGTERM in relayd = 0
FixedAdded Store::flush(timeout) (FIFO drain, overridden by the Firestore mirror) and a SIGTERM/SIGINT handler that drains the durable queue before the driver loop exits.
MediumF-22Infra · IAMFixed

The build service account is owner-equivalent, and the "no owner" comment is false

The push-to-main build and deploy account holds editor plus project IAM admin plus service-account admin plus secret-manager admin plus storage and run admin. Project IAM admin carries setIamPolicy, which in this in-org project can grant owner, so the code comment "no owner-granting" and the commit that claims it dropped owner are both wrong. Secret-manager admin includes versions.access, so the pipeline can read the relay root seed directly. Combined with auto-approve apply on every push, one bad commit to main is full project takeover plus fleet identity theft. Bounded by single-maintainer main-push, but the false hardening claim will mislead the eventual production pass.

EVIDENCEinfra/cloudbuild_trigger.tf:37-58 (roles), false comment at 44-45 · commit 33c2bee
FixedCorrected the false "no owner-granting" SA comment (it IS owner-equivalent) and documented the narrowing to do before production.
MediumF-23Infra · identityFixed

Identity secrets mount as "latest", so a rotation silently re-keys the fleet

Both the relay identity and the example endpoint identity mount the latest secret version. Adding any new version silently re-keys each region on its next cold start (regions scale to zero and resolve latest at start), so the fleet runs split-brained while orphaning Firestore partitions, registry entries, and pinned client relay addresses. The endpoint's derived address then diverges from the address hardcoded in TF and published in DNS, silently killing HNS resolution, with no drift detection.

MediumF-24ObservabilityFixed

No monitoring, alerting, or SLOs for the 42-region fleet

There is not a single monitoring resource, uptime check, alert policy, SLO, or notification channel in infra, and all logging is unstructured stderr with no severity, so even log-based alerting cannot tell an error from a stats line. Every failure mode is invisible: region crash-loop or OOM, Firestore quota or IAM failures that silently kill handoff and P5 delivery, cert-renewal failure, and the known reconnect churn. The current observability is a human curling the netlog stream.

§ 05 / 07 Persistence · SDK boundary

The strongbox is open

The on-device database is the declared ground truth and holds live forward-secrecy keys. In-code comments and DESIGN.md both claim it is encrypted. It is not, and the FFI open path can silently downgrade it to amnesia.

MediumF-25PersistenceFixed

hop.db is plaintext despite an in-code claim that it is encrypted

The driver comment asserts the encrypted database has no plaintext mirror, but the store uses plain bundled SQLite (not SQLCipher), the doc says encryption is layered at open time while nothing layers it, and open passes the raw path through with no cipher. So the table holds double-ratchet root, chain, and skipped keys, content keys and signing seeds, and plaintext outbound bodies, plus the driver writes a plaintext messages mirror anyway. DESIGN.md marks at-rest encryption as decided and implemented and builds a data-protection argument on at-rest exposure being essentially nil. Your own device db-pull workflow trivially extracts live keys.

EVIDENCEHopBearer.swift:1815 (false claim) · Cargo.toml:40 (bundled, not sqlcipher) · hop-store-sqlite/src/lib.rs:12-13 · keys at session.rs:64-76, hps.rs:82-99 · DESIGN.md §13.2
FixedCorrected the false claims, THEN built the real thing: a sqlcipher feature (SQLite + SQLCipher, vendored OpenSSL) and open_keyed(path, key) that keys the db before any table access. The key threads all the way through — HopNode::open_keyed (UniFFI) + hop_node_open_keyed (C ABI, HOP_ABI_VERSION 2) + Kotlin/Swift openKeyed. A test proves a keyed db is unreadable without the key (plain and wrong-key opens both fail); CI runs it. And it is now WIRED for the apps: the iOS/Android build scripts build libhop with --features sqlcipher by default, and both drivers open via openKeyed with a device-derived 32-byte key (domain-separated from the identity seed, never in the db). iOS is already sqlcipher-built and encrypting; Android encrypts on the next build-aar.sh (NDK).
MediumF-26SDK · FFIFixed

hop_node_open silently falls back to in-memory storage on a bad path

Open tries the sqlite path or else opens in memory, so a bad, read-only, corrupt, or future-incompatible file yields a working-looking node whose sessions, pending sends, and custody bundles silently evaporate on restart, and nothing repairs the file, so every launch takes the same fallback forever. The header and both wrappers document "NULL only on an invalid path", the opposite of the behavior. There is no persistence signal for the host to detect the downgrade, and an in-memory node makes the external test harness lie.

EVIDENCEcore/hop/src/lib.rs:423-426 (or_else in-memory) · sdk/hop.h:31 (contradicting doc)
Fixedhop_node_open quarantines an unusable db and reopens fresh; added an is_persistent signal and catch_unwind on the C constructors.
LowF-27SDK · KotlinFixed

The Kotlin HopNode is leak- and use-after-free-prone

It owns a raw pointer with a bare free, implements neither AutoCloseable nor a Cleaner, and never nulls the pointer after free, so a dropped node leaks the Rust node and store and any post-free call passes a dangling pointer. The Swift wrapper avoids this with deinit, an asymmetry between the two template wrappers. The header calls the node reference-counted but exports no retain, so concurrent free versus tick is an unavoidable UAF with no documented rule. Capped at Low because the shipped app drives the node via UniFFI bindings, not this wrapper.

EVIDENCEHop.kt:100 (bare free) vs Hop.swift:57 (deinit) · hop.h:22 ("reference-counted", no clone)
FixedKotlin HopNode is now AutoCloseable with an idempotent close() that nulls the pointer, plus a Cleaner backstop.
LowF-28SDK · ABIFixed

hop.h has no ABI version symbol or negotiation

The contract exposes no version macro, version function, or capability query. Kotlin binds the library dynamically, so a wrapper newer than the loaded object fails with an unsatisfied-link error mid-session, and a semantically-changed function drifts undetected.
