The 5 regressions the #40 fixes introduced (all fixed)

Each was confirmed in code by the adversarial pass. All five are fixed in the follow-up commit. Four were latent (dead-code teardown paths or doc); only the RelayBearer executor race was live-reachable.
mediumRestart path runs two executor threads concurrently over non-volatile bearer state (new race introduced by the var-swap fix)✓ fixed
Where
RelayBearer.kt
Detail
CONFIRMED. stop() submits teardown T1 on the old exec (:118) then calls exec.shutdown() (:131) with NO awaitTermination; start() sees exec.isShutdown (:100), installs a NEW exec, and runs T2/dial() on a different thread (:101). grep confirms ZERO @Volatile/synchronized/awaitTermination in the file, so started/up/ws/stableFuture are plain non-volatile fields written by two threads with no happens-before. Real ordering race: if T2 reads the still-true started (T1 has not yet cleared it) its `if (started) return@execute` early-returns, then T1 tears down, leaving started=false/ws=null with no reconnect (scheduleReconnect gates on started) - bearer silently dead after restart. Visibility variant also holds. Genuinely newly introduced by the r5/#40 var-swap (exec was a `val` pre-r5, so only one executor ever existed). The lifecycle test asserts only isShutdown, never started/ws/a real socket, so it cannot catch this - matching the project's fix-round-regression pattern.

Completeness critique

The critic's read on whether the closures held and what is still open.

Both load-bearing claims verified on disk at HEAD 3750608. Endpoint has 20 guard_core/catch_unwind sites; gateway has zero yet calls node.handle/send_http_response/tick/take_http_requests/drain_outgoing directly on the main thread over attacker-controlled bundle bytes. RelayBearer's exec is a var with all lifecycle fields (ws/started/up/stableFuture) plain non-volatile and zero @Volatile/awaitTermination/synchronized; its lifecycle test asserts only isTornDown (its own comment admits it), so the race is invisible to CI. Here is the pass-6 critic verdict.

(1) Did the #40 fixes hold?

Yes, every one held its claimed invariant. All eight #40 closures verify: relay WS-accept no longer charges a mesh slot before classification (all three sub-claims), Apple dedup/wasSurfaced intact, Android relay executor restartable + guarded callbacks + shared dispatcher untouched, Android driver inst=null synchronous, Kotlin defensive-copy accessors full, WASM stale-pkg deferral sound, infra silent-region/heartbeat removal clean, CI orphan-LICENSE removal + guard update on all four sub-claims. Ground truth is fully green: 333 Rust tests + clippy clean, 56 Swift, 44 Kotlin, WASM 2.9M checks 0 failures + 15/15 scenarios deliver+ack, all guards pass, header byte-identical + cbindgen-fresh, ABI=2 consistent across all five locations.

But five fixes each carried in a NEW regression (isNew=true). Calling out every one:

• MED, live - RelayBearer executor race (RelayBearer.kt). The val→var swap that made the executor restartable introduced a cross-thread data race over non-volatile started/up/ws/stableFuture. stop() runs teardown on the old exec with no awaitTermination, start() installs a fresh exec and runs dial() on a different thread; a bad interleave leaves the bearer silently dead after restart. This is the only new regression in live-reachable code.

• MED, doc - "No foreground service exists" (partial). The false phrase is in the #40 *commit message*, not the shipped KDoc (the KDoc is accurate). So this is a commit-hygiene miss, not a code defect.

• LOW, dead code - inst=null unlocked/unconditional (HopBearer.kt). Bare inst = null outside synchronized(this), no identity check; could orphan a newer instance if teardown() ever raced re-creation.

• LOW, dead code - transient SQLCipher double-open (HopBearer.kt). Synchronous inst=null + deferred node.close() opens a window where a fresh instance opens the same hop.db before the old handle closes.

• LOW, doc - stale observability.tf header. The silent-region removal left a header still claiming "(c) a silent region" is instrumented via log-absence, directly contradicting the new NOTE in the same file.

Four of the five are latent (three sit in teardown(), which has zero callers) or comment-only. Only the RelayBearer race bites in production.

(2) Is the regression-introduction pattern broken?

No, but it is decaying. #40 still shipped five new findings, matching the project's fix-round-regression signature. The root cause is unchanged and mechanical: fixes land in the Android platform layer (5-8% coverage) with tests that cannot catch the regression they introduce. The RelayBearer lifecycle test asserts only isTornDown and never touches started/ws/a socket, so it is structurally blind to the race the same PR created. That is the identical failure mode as every prior round.

What *has* improved: severity and blast radius are way down versus earlier passes. Four of five new findings are dead-code-latent or doc-only. The pattern breaks only when the platform layers get real state-machine tests, which has not happened.

(3) Which grades are too generous?

• Endpoint + Gateway: C+ is too generous → C-/C. It carries a confirmed HIGH: the gateway driver loop is missing the core-panic guard its sibling endpoint has 20 of, so one malformed bundle from any mesh peer unwinds run() and kills the whole process. The closure note even concedes the "only two LOWs open" claim was NOT held because this higher item exists. A live, remote, unmitigated crash-DoS with a one-line proven fix does not belong in a C+.

• Protocol core: A- is slightly generous → B+. The traced-ACK/AckTo vaccine is authenticated but not authorized: any observer can forge a "Delivered" and suppress a bundle network-wide for up to 7 days (MAX_SEEN_LIFETIME, not the 24h the note first assumed). The code comment claims "no CDH proof possible" while an origin-side authorization check (acker src vs the delivered bundle's dst) is demonstrably feasible. A forgeable network-wide suppression primitive in the core keeps it off an A-tier.

• Apple driver: C+ is borderline. A release build still writes automation.json (self address + last 100 plaintext messages) if HOP_AUTO is injected; writeAutomationDump() is gated only at runtime, not #if DEBUG-compiled-out. Gated by needing a trusted/unlocked device, so it survives at C+, but it is a direct hit on Hop's privacy thesis and should be flagged.

The Android D/D/F grades and the platform coverage F's are honest, not inflated.

(4) Net vs pass 5

Slightly worse on paper, better in reality. Quality GPA across these 14 subsystems computes to ~2.77 (A-/A-/B-/A-/B-/C+/B-/C+/D/D/C+/A-/B+/A-), down ~0.26 from pass 5's 3.03. That dip is not new rot: 32 fixes landed and all held, with exactly one live new regression. The decline is the confirming pass grading the two Android subsystems at D and finally pricing in the HIGH gateway crash-DoS and near-zero platform coverage that pass 5 graded more charitably. Read it as grading honesty catching up to the code, not the code regressing.

Single most important thing still open: the gateway core-panic guard gap (HIGH). It is the only HIGH, it is live and remotely triggerable on attacker-controlled bytes, the fix is the exact guard_core/catch_unwind pattern already revert-proven in the sibling endpoint, and it is the very class the endpoint deemed must-fix. #40's "only two LOWs open" note omitted it.

Priority-ordered next actions (no time estimates)

1. Close the HIGH. Wrap gateway run()'s node.handle/tick/take_http_requests/send_http_response/drain_outgoing (main.rs:216-274) in guard_core, mirroring endpoint main.rs:498-597, and add the revert-proven regression test analogous to guard_core_converts_a_core_panic_into_a_logged_skip.

2. Fix the one live new regression (RelayBearer race). Serialize start()/stop() under a single lock, or make started/up/ws/stableFuture @Volatile and awaitTermination the old exec before start() reinstalls; add a lifecycle test that asserts started/ws state after restart, not just isTornDown.

3. Fix the gateway 503 dedup-poison (MED). Move the fulfilled insert to after the fetch (match fulfill() at lib.rs:324) so a shed 503 "busy" is retryable instead of locked out for the full dedup TTL.

4. Resolve the Android driver dead-code cluster in one pass. Either wire teardown() into HopService.onDestroy (the one-liner) or delete it as dead code; if kept, make inst=null identity-checked under synchronized(this) and order node.close() ahead of the swap to kill the double-open window. Correct the commit-message misstatement going forward.

5. Compile out the Apple automation mirror (MED). Put writeAutomationDump() behind #if DEBUG, not just a runtime gate, so a release build cannot write plaintext even with HOP_AUTO set.

6. Add origin-side authorization to the traced-ACK path (MED). Compare the acker's src to the delivered bundle's dst (the origin still holds it) before flipping delivered/removing, and fix the "none is possible" comment.

7. Correct the observability.tf header (LOW). Drop the now-false "(c) silent region" instrumentation claim to match the in-file NOTE.

8. Systemic, the only thing that actually breaks the pattern: start the platform-layer coverage round the memory already flagged. Extract the Android bearer/driver decision cores (executor lifecycle, teardown ordering, RelayBearer backoff/429) and the Apple driver codecs into tested pure functions, and add lifecycle tests that assert state rather than isShutdown. Every fix-round regression to date has lived exactly where coverage is 5-8%.
