# Hop — Prioritized Gap Report

## State of the build

The last ~4 weeks landed a large, coherent body of work: the libhop C-ABI rewrite (`sdk/hop.h` as the universal client+bearer contract, Swift/Kotlin wrappers, four isolated Apple bearer packages, Android bearer modules, ESP32 client, both app cutovers, and the `crates/ -> core/+services/+examples/` tree migration + `hop-ffi -> hop` rename), the §39 "untraceable-by-default" P1–P5 delivery path (recognition/mailbox tags, private bundles, receiver-beacon gradient routing, blind-spool + want-beacon pull), BLE L2CAP/GATT reliability, multi-peer flood/securing fixes, the Spacelift→GCS-state+Cloud-Build GitOps migration, the `sh.hopme.*` rename, the `InternetEgress` removal, Wi-Fi Direct removal, optimistic send, and Font Awesome icon sweeps. The 128-test hop-core suite is green, §39 P1–P5 were production-verified on the 6-device fleet, and identities survive reinstall. Overall the protocol and app layers are functionally healthy for a pre-prod, single-maintainer, iterate-freely project.

The health picture darkens along three axes that the feature work outran. **First, there is no safety net around the wire/ABI contract or the fleet deploy:** push-to-main auto-applies all ~42 relay regions with zero `cargo test`, the contract-purity guardrail runs nowhere, and the "versioned" wire format has a `BUNDLE_VERSION` field nothing ever reads — which already bricked the deployed relay once (the `InternetEgress` index shift). **Second, the §39 privacy story has real gaps between the design's stated guarantees and the code:** the receiver-beacon gradient can be hijacked/black-holed by any mesh participant (contradicting a written §39 invariant), and the mailbox-tag is a publicly computable, never-rotating hash of the openly-flooded prekey, deanonymizing reachable recipients. **Third, the bearer cutover and the persistence layer both silently dropped recovery behavior:** the shared bearers lost the Android BT off/on self-heal and the Apple LAN dial timeout, and `rehydrate()` silently discards any persisted struct whose layout changed (which already ate the deferred-send queue when `PendingContent` gained a field mid-fleet). Nothing is critical after adversarial correction, but the top of the High list is one binding-check away from a critical §39 route hijack.

No findings survived at Critical severity after verification. The highest-severity confirmed items are grouped below.

## High

### 1. §39 receiver-beacon gradient can be hijacked / black-holed — mailbox-tag is never bound to its signer
*(merged: core-protocol + security-privacy; finder flagged Critical, both verifiers corrected to High)*
DESIGN.md:2386-2387 states "only the holder of M can advertise a gradient for M. No node can hijack or black-hole a prefix it doesn't own," and DESIGN.md:2466 repeats "signed beacons stop hijack." The code enforces neither. `RecvBeacon` carries only `{ mailbox: Tag, prefix_bits }` with no SPK (`core/hop-core/src/discover.rs:89`); `Advert::verify()` (`discover.rs:164-174`) checks only the identity signature over the body, never `mailbox == mailbox_tag(publisher's prekey)`. Beacons are signed by the node's *identity* key, not the prekey the design claims. Since `mailbox_tag = H(SPK_public)` (`crypto.rs:342`) and the SPK floods in cleartext, any mesh participant can publish `RecvBeacon{mailbox: victim_M}` with a high `seq`, self-signed; `on_advert` (`node.rs:3349-3362`) installs it and `record_gradient` (`node.rs:3379`) supersedes the legit gradient "even from a new direction." `offer_bundles_to_link` then routes every private bundle for M *only* down the attacker's link (`node.rs:3491-3498`, `continue` skips all others) — a targeted black-hole of the flagship untraceable-delivery path. Amplification: the forged mailbox also enters `wanted_mailboxes` (`node.rs:3403-3407`), so the relayd want-beacon worker (`services/hop-relayd/src/main.rs:1004-1030`) drains the victim's Firestore blind spool toward the attacker. Content stays sealed (no confidentiality break), which is why it's High not Critical. **Next step:** on ingest, look up the publisher's PreKey advert and reject any beacon where `mailbox != crypto::mailbox_tag(&publisher_spk_pub)` before recording a gradient; add a non-owner-rejection test; correct the false claims in the `discover.rs` comment and DESIGN.md once enforced.

### 2. Mailbox-tag is publicly linkable to identity and never rotates — defeats §39 pseudonymity for reachable recipients
*(security-privacy, High)*
`mailbox_tag(spk_pub) = BLAKE3("hop mailbox tag v1", spk_pub)` (`crypto.rs:342-344`) is a deterministic hash of the recipient's signed-prekey public, which floods in cleartext in the `PreKey` advert whose `publisher` field is the node's address (`discover.rs:71,100`, reserved `_keys` topic). Any relay or global observer can compute `H(spk_pub)` for every known address and build a complete mailbox-tag→address table. Worse, the P4 `RecvBeacon` rides an `AdvertBody` whose cleartext `publisher` is the address, so it publishes "address A owns mailbox M" verbatim (`node.rs:1205-1220`) — no hash table even needed — and this is the default (`route_to_me: true`, `node.rs:638`). `derive_prekey()` is deterministic with no epoch input (`crypto.rs:105-115`, comment says rotation "when added"), so the "rotatable pseudonym" never rotates. This deanonymizes the P4 gradient, the P5 blind spool (`mailboxes/{tag_b58}/bundles`), and the private delivery-ACK (`node.rs:1300-1304`). DESIGN.md:2465 falsely asserts in present tense that "mailbox-tags rotate per prekey-epoch." **Next step:** derive the mailbox-tag from material absent from the public prekey advert (epoch-keyed or per-contact shared secret), de-address-ify the beacon (sign with the prekey, not the identity), implement prekey/mailbox epoch rotation, and correct DESIGN.md:2465.

### 3. Single `Mutex<Node>` + per-inbound full-store rescan keeps the "Securing forever" congestion-collapse vector live
*(core-protocol, High)*
The whole node is behind one `Mutex<Node<SqliteStore>>` (`core/hop/src/lib.rs:392`), and every FFI/C-ABI entry point takes it (`lib.rs:454-465`; `cabi.rs` wraps the same node). WAL (#3) and the O(N) utility precompute landed, but `offer_bundles_to_link` still does a full-store scan (`store.have().ids` then per-id `store.get`, `node.rs:3451-3477`) on every accepted relayed bundle (`node.rs:3243-3247`), every newly-accepted receiver-beacon (`node.rs:3411`), and every link-up. The in-code comment at `node.rs:3462-3465` names this exact read-storm as what "starved link Noise handshakes and prekey gossip, which is what made messages hang 'Securing' under load." The store is bounded to ~128 relayed bundles, so the constant shrank, but a burst still costs O(bundles × links × store) SQLite reads + postcard decodes under the one lock Noise handshakes need — the same mechanism that produced a user-visible fleet failure, and §39 added more offer triggers. **Next step:** make offer incremental (offer only the just-arrived bundle plus a bounded work-queue), and/or split lock granularity so link handshake/gossip state isn't behind the bulk-offer mutex.

### 4. No wire-format versioning: `BUNDLE_VERSION` is written but never read, not bumped on the breaking `InternetEgress` removal, and there are no golden-vector tests
*(merged: core-protocol + services-infra + testing-ci; verifiers split medium/high — rated High for the combined issue, which already caused a production outage)*
`BUNDLE_VERSION = 1` (`bundle.rs:23`) is stamped on every bundle (`bundle.rs:371,415`) but never read on decode or in `verify()`; `Bundle::from_bytes` (`bundle.rs:540-541`) is bare `postcard::from_bytes`. Commit `5dd64d3` removed `Destination::InternetEgress`, shifting postcard variant indices (AckTo 2→1, Broadcast 3→2) without bumping the version — the commit message itself says "postcard variant indices shift → full fleet + relay must rebuild." This is the exact mechanism that left the deployed relay unable to decode new-core traffic. Ingest drops undecodable frames silently (`node.rs:2788` `else`), and the Firestore rehydrate path skips undecodable spooled bundles (`hop-store-firestore/src/lib.rs:53-56`). No golden-byte fixtures or cross-version decode tests exist anywhere; existing serialization tests are same-binary round-trips that cannot detect a wire break. `ADVERT_VERSION` (`discover.rs:125,149`) has the identical write-only pattern. **Next step:** check `version` in `Bundle::from_bytes` and reject with a distinct logged `Error::UnsupportedVersion`; adopt append-only enum discipline (or reserved variant slots) so removals never renumber; commit golden-vector fixtures per Payload/Destination variant; bump `BUNDLE_VERSION` on every layout change; add a link-level hello/version exchange so mismatched peers fail loudly.

### 5. `rehydrate()` silently discards any persisted struct whose postcard layout changed; `PendingContent` actually changed mid-fleet (6bb5739)
*(persistence-upgrade-compat, High)*
`Node::rehydrate` decodes every persisted blob with bare `if let Ok(...)` and drops on `Err` with no log/counter (`node.rs:713-772`): hps ServiceConfig, subscriptions, `pending_content`, invites, `session/` PeerSession ratchet state. postcard is positional and none carries a version tag, so any field add/remove/reorder silently vanishes the state on upgrade. Not hypothetical: `6bb5739` (2026-06-28, §39 P3) appended `private: bool` to `PendingContent` while the fleet ran the 06-27 build, so any in-place upgrade with queued "Securing…"/deferred sends lost the entire queue (`node.rs:756-760`; the `tx` handles keeping the UI "Sending…" alive are only created on successful decode). `PeerSession`/`Session` layouts happen to be unchanged since `466ba39`, which is the *only* reason ratchet sessions survived — the next field added to `PeerSession` silently discards every forward-secret session on upgrade, producing peer-side ratchet desync (the "Securing forever" class) with zero telemetry. postcard is pinned (`Cargo.toml:30`), so struct layout is the live risk. **Next step:** wrap each persisted blob in a 1-byte-versioned envelope with explicit version dispatch, and at minimum log/count decode failures and surface them to the host so a silent state wipe is observable; add a golden-fixture compat test.

### 6. Android production path lost the BT off/on recovery: shared `BleBearer` can't survive an adapter toggle and can't start with BT off
*(bearers, High)*
`useSharedBearers` defaults `true` (`HopConfig.kt:25`), but `registerBtStateReceiver()` — the documented "proven recovery" for a wedged BLE stack — sits only in the legacy `else` branch (`HopBearer.kt:323`) and even then rebuilds only the legacy peripheral. The shared `sh.hopme.bearers.ble.BleBearer` has zero `BluetoothAdapter` state handling (grep for `ACTION_STATE_CHANGED` across `bearers/android` = 0 hits): its L2CAP accept thread `break`s on IOException and is never restarted (`BleBearer.kt:314-325`), and nothing re-opens the GATT server/advertiser/scanner after STATE_ON. So a BT toggle (user action, airplane mode, battery saver, or the very recovery the comments recommend) leaves the device permanently deaf on BLE until app force-stop. Worse, `Peripheral.start()` calls `adapter.listenUsingInsecureL2capChannel()` unguarded (`BleBearer.kt:310`); if BT is off at launch the IOException propagates through `BearerManager.start`'s unisolated `forEach` (`Bearers.kt:48`) on the plain HandlerThread, aborting LAN + relay startup too (likely crashing the process). Matches the open "BLE advertiser/link-formation wedges after restart" memory item. **Next step:** register a `BluetoothAdapter.ACTION_STATE_CHANGED` receiver on the shared path that stop()s/re-start()s the shared `BleBearer`, wrap each bearer's `start()` in try/catch inside `BearerManager.start`, and restart the L2CAP accept loop after transient IOExceptions.

### 7. Apple LAN bearer: no dial timeout, reaper armed only on `.ready`, and listener/browser failure never recovers
*(bearers, High)*
`LanLink` creates its no-HELLO reaper and liveness timers only inside `onReady()` (`LanBearer.swift:91-98`); the `stateUpdateHandler` handles `.ready/.failed/.cancelled` and ignores `.waiting` (`swift:71-83`), NWConnection's default state on ECONNREFUSED/unreachable (stale Bonjour record for a restarted peer, sleep/wake). So a wedged dial: the `LanLink` self-retains forever (`swift:81`, released only in `close()`), and the peer's hex stays in the `dialing` set forever (removed only in the dial-link's `onClose`, `swift:263-270`), permanently blacklisting that peer for the process lifetime — and the greater-id tiebreaker means the peer won't dial back. Separately, both the NWListener and NWBrowser handlers only log on `.failed` with no restart (`swift:236,258`), so after a Wi-Fi transition/sleep-wake the device silently stops accepting and discovering on LAN until relaunch. The legacy path's `restartLan()` did this recovery on every foreground; the shared cutover dropped it on the false assumption the bearer self-manages (`HopBearer.swift:490`). Android's LAN dial has a 5s timeout (`bearer-lan/.../LanBearer.kt:54,352`), so this is Apple-specific. **Next step:** arm the reaper from `LanLink.start()`, handle `.waiting` with a dial deadline that cancels the connection, and restart the listener/browser on `.failed` with backoff.

### 8. Zero CI for code + push-to-main auto-deploys the fleet ungated; the contract-purity guardrail runs nowhere
*(merged: sdk-abi + testing-ci + observability-ops; verifiers split medium/high — rated High)*
The only GitHub workflow is `pages.yml` (site deploy). The Cloud Build GitOps trigger fires on every push to `^main$` with no path filter (`infra/cloudbuild_trigger.tf:76`) and runs exactly: docker build ×2, push ×2, `tofu apply -auto-approve` — no `cargo test`, clippy, contract-purity, header-drift check, smoke test, canary, or rollback (`infra/cloudbuild.trigger.yaml`). `tools/codegen/check-contract-purity.sh` (added deliberately in `587b6e8`) has zero callers (repo-wide grep), `.git/hooks` has only samples, and `core/hop/regen-header.sh` is manual with no drift check (`cabi.rs` has zero `#[test]`s). The Docker build catches non-compiling pushes, but a commit that compiles yet regresses behavior or the wire format rolls to all regions with the only detection being a human curling `relay.hopme.sh`. This is the exact failure class that already bricked the relay (finding #4). `cargo test --workspace` = 169 passing locally, so a gate would be green today. **Next step:** add a `ci.yml` running `cargo test --workspace` + clippy + `check-contract-purity.sh` + `cbindgen regen && git diff --exit-code sdk/hop.h` on every PR/push; gate the Cloud Build apply on a green check; add a post-apply smoke step (curl one region for the `== hop relay ::` header + one WS upgrade). Canary/staged-region rollout is a reasonable later phase for a 6-device fleet.

### 9. `hop-relayd` (the §39 P5 spool/want-beacon worker) has zero tests; cross-region spool→pull is untested anywhere
*(testing-ci, High)*
`services/hop-relayd/src/main.rs` (~1064 lines) contains the production handoff worker implementing §39 P5 blind-spool and want-beacon pull (`spool/wanted` at `main.rs:436-437`; spooled/pulled dedup with an unbounded-growth `if spooled.len() > 100_000 { clear() }` at `main.rs:915-924`) and has 0 `#[test]` functions (the one `tests/ws_bearer.rs` covers only WS framing). The core-level `spool_then_want_beacon_reloads` (`node.rs:4477`) covers a single in-memory relay node; the 12 hop-relay lib tests (region.rs, backbone.rs, lib.rs) contain no spool/want-beacon coverage. So the explicit cross-*region* spool→beacon→pull path — arguably the dominant real-world offline-delivery path in a ~42-region fleet, and the mechanism that resolved the §39 default-relay regression — has no automated coverage at any layer, and prior fleet verification never exercised it either. **Next step:** extract the relayd handoff worker into a testable module; add an integration test with two `Region` mailboxes + a fake store: spool in region A, beacon in region B, assert the bundle is pulled, re-ingested, delivered exactly once, and that the 100k `clear()` cannot double-spool (Firestore keys by bundle id, so worst case is redundant writes, not duplicate delivery).

### 10. DESIGN.md still specifies `Destination::InternetEgress` and gateway-gradient routing that no longer exist
*(docs-drift, High)*
DESIGN.md is the protocol spec and the contract for the multi-language implementer story (ESP32 C client, `hop.h` consumers). §5 (`DESIGN.md:171-173`) defines `Destination = Device | InternetEgress | AckTo`; the code enum is `Device | AckTo | Broadcast` (`bundle.rs:30-39`) — `InternetEgress` was removed in `5dd64d3` and `Broadcast` (which IS on the wire and index-shifting) isn't in §5 at all. §6 (`DESIGN.md:235-240`) still describes gateway-gradient routing of `InternetEgress` bundles with no code counterpart (egress now rides device-addressed `hops://`, `services/hop-gateway/src/lib.rs:170-176`), and §39 still references "the want-beacon / `InternetEgress` pull verb" (`DESIGN.md:2529`). Later sections cite §5 as defining `Broadcast`, so the spec is internally inconsistent. Anyone building a decoder from §5 produces a wire-incompatible enum with no removal note or versioning story to warn them — the exact drift that already bricked the relay. **Next step:** update §5 to the real enum with a dated removal note explaining why; rewrite §6's egress subsection to the device-addressed `hops://` gateway path; fix the §39 reference; add a wire-format versioning/compat note.

### 11. Relay netlog mirrors delivery metadata into GCP Cloud Logging with default 30-day retention
*(observability-ops, High)*
`LogHub.emit()` mirrors every netlog line to stderr explicitly "(so it also lands in Cloud Logging)" (`main.rs:94-98`, unconditional `eprintln!`). Those lines include device-address prefixes on connect/leave (`main.rs:411-416`), ingest/handoff destinations + region (`main.rs:385,966-971`), spool mailbox-tag prefixes (`main.rs:992-996`), and want-beacon pulls (`main.rs:1019-1023`). Each region is a separate Cloud Run service, so Cloud Logging region-tags and timestamps every line — exactly the "pseudonymous address → coarse location + activity timeline" that DESIGN.md:1753-1756 names as the most sensitive dataset in the system and that §33 (line 1748) claims is "ephemeral compute or on-device" only. `infra/` has no `google_logging_project_bucket_config`, exclusion filter, or retention override (grep exit 1), so it persists in the `_Default` bucket for 30 days, readable by anyone with project log-viewer access. This is distinct from the public-stream leak (finding below) because the stderr mirror is independent of `serve_log_stream`. **Next step:** add a `google_logging_project_exclusion` or short-retention bucket for the relay services (removes at-rest persistence without touching the live debugging stream); as a follow-up, drop/per-boot-salt the address/tag prefixes in the operator sink.

### 12. No liveness probe; the only fleet-health signal is the public log stream slated for removal, and it isn't a valid health signal anyway
*(observability-ops, High)*
`serve_log_stream` runs on per-connection threads serving the ring backlog + `: ping` keepalives (`main.rs:132-168`) independent of the single-owner driver loop (`main.rs:366-441`). If the driver deadlocks, TCP accepts and the stream keep working while the node relays nothing; the only tell is the 10s `stats:` lines stopping, requiring a human watching. Worse, the Firestore liveness heartbeat runs on its own detached thread (`main.rs:801-806`), so a wedged node keeps advertising itself "warm" to the handoff layer. `cloud_run.tf` defines no `startup_probe`/`liveness_probe` (`cloud_run.tf:21-98`), so Cloud Run's default TCP check passes for a wedged instance and never restarts it, and with `max_instances_per_region=1` a wedged instance IS the region. There is no `/healthz`, metrics endpoint, or authenticated log variant. This creates a hard ordering dependency: the security work to remove the unauthenticated public stream (below) must not land before a replacement exists, or the fleet goes fully blind. **Next step:** add a `/healthz` in `serve_ws`'s HTTP branch returning 200 only if the driver loop ticked within N seconds (shared `AtomicU64` last-tick), wired as the Cloud Run startup+liveness probe; add an authenticated/de-identified log tap before removing the public stream. (Do NOT add an external uptime check against region endpoints — DESIGN.md:1436 forbids externally probing regions since it wakes scaled-to-zero instances; a container-level probe is fine.)

### 13. Deployed internet-facing `hop-endpoint` has no abuse controls and unbounded thread spawning
*(hops-hns-endpoint-surface; finder and verifier both High — but see the medium recalibration below)*
`services/hop-endpoint` is deployed always-on (`infra/example.tf` min=1, invoker `allUsers`) at `example.hopme.sh`. It parses untrusted `hops://` request bundles and reverse-proxies plain-HTTP connections with NO per-source rate limiting, dedup, connection/concurrency cap, or panic isolation (grep for rate/limit/semaphore/dedup/catch_unwind = none). The accept loop spawns one unbounded OS thread per inbound TCP connection (`main.rs:133-136`) and one more per hops request (`main.rs:284`); established WebSockets set `read_timeout(None)` and loop forever, so opening many connections exhausts threads/memory on the 512Mi single instance. The orphaned `hop-gateway` crate implements exactly the controls DESIGN.md:344 demands (`GatewayConfig` dedup/rate-limit/size caps, 5 tests) — they live in dead code. **Recalibration note:** the intent analysis argues Medium is fairer — the driver runs on the *main* thread so a parse panic aborts the process and Cloud Run restarts it (no zombie accept loop), `max_instances=1` bounds cost, and this is a demo endpoint outside the fleet delivery path touching no hard policy. Treat as a High-labeled/Medium-priority hardening item. **Next step:** port `GatewayConfig`/`is_rate_limited` from hop-gateway (bounded connection semaphore + per-source sliding-window limiter + dedup), wrap the driver's `node.handle` in `catch_unwind`, and add an integration test asserting a mismatched signed host is rejected with 403 before any backend fetch.

## Medium

### Private (§39) bundles are unauthenticated with no inbound rate limit or dedup-table cap
*(core-protocol, Medium)* `Bundle::create_private` sets `sig: Vec::new()` and `verify()` passes for any sealed bytes where `compute_private_id(payload) == id` (`bundle.rs:434,460-469`), so any node can mint unlimited valid private broadcast bundles. There's no per-link/per-peer ingest rate limit (grep), and the SQLite `seen` dedup table is pruned only by attacker-set `lifetime_ms` (u32, up to ~49.7 days) with no row cap and no delete on bundle eviction (`hop-store-sqlite/src/lib.rs:51,72-87,99-105,135-142`), so it bloats for weeks. DESIGN.md:2464-2468 makes caps+rate-limits the explicit compensating control "from day one." Relayed bundle bodies ARE capped at 128 (`evict_relayed_if_needed`) and the gradient table IS capped (`MAX_RECV_GRADIENT=4096`), so the amplification is bounded; the genuinely unmitigated sinks are the `seen` table and the unclamped `lifetime_ms`, and the surface reaches the internet-facing relay + paid Firestore. **Next step:** clamp accepted `lifetime_ms` on ingest, cap/LRU the `seen` table, add a per-link inbound token-bucket, and delete `seen` rows on bundle removal.

### Optimistic send has no failure state — a throwing core send leaves the bubble on "Sending…" forever, on both platforms
*(apps-drivers, Medium)* The bubble is inserted with `bundleId=null` and patched later. If `node.sendMessage` throws (FfiError: store/DB error, sealing failure — `core/hop/src/lib.rs:489-504`), `stampSent` re-writes `bundleId=null`, `failed` is never set, delivery tracking skips the row (`if m.bundleId == null continue`), and the message silently never sends. Android: `HopBearer.kt:504-518,1475`; iOS: `HopBearer.swift:690-702`. The retry affordance is gated on `m.failed` (`MainActivity.kt:764-772`), so it never engages; the only `failed=true` writer is manual `clearQueue()`. The common "peer unreachable, no prekey" case correctly defers (doesn't throw), so this fires on real store/seal errors — rare but silent message loss with the error swallowed by `runCatching`/`try?`. **Next step:** when the id comes back null/nil, set `failed=true` and log the error so the existing "Not sent · tap to retry" path engages; fix both platforms together.

### Cutover is still bounded: apps run the pre-rewrite monolith drivers; the north-star `drivers/` packages are consumed by nothing; beacon UUID duplicated 4×
*(apps-drivers, Medium; overlaps docs-drift #libhop and the Multipeer/WFD low item)* `a438129`/`d2c4471` re-pointed the OLD monolith drivers (`apple/HopDriver`, `android/HopDemo/hop-driver`) at the new bearer packages, but the apps never moved to `drivers/apple` + `drivers/android` (consumed only by docs + a Gradle compile check; namespace `sh.hop.driver` inconsistent with `sh.hopme.*`). The monoliths still carry full legacy transports as flag-off code, `hopmac` PINS `useSharedBearers:false` (`hopmac/main.swift:32`) making the "slated for removal" legacy BLE path load-bearing for the test tool, the iBeacon UUID is defined byte-identically in 4 files (`HopBearer.swift:161`, `BeaconWake.swift:23`, `HopBearer.kt:2104`, `BleBearer.kt:70` — the historic F0900BEA drift bug), and iOS runs TWO concurrent beacon monitors (the facade `CLLocationManager` + `BeaconWake`). The UUID matches everywhere today so wake works; the gap is the 4-way duplication reproducing the preconditions of a past silent-wake regression. **Next step:** consolidate `HOP_BEACON_UUID` to one shared constant per platform, delete the facade beacon monitor on iOS, give the shared `BleBearer` a central-only mode so `hopmac` can drop the pin, then excise the legacy transports and adopt-or-remove the orphaned `drivers/` packages.

### Font Awesome Pro (commercial-license) icon sources are committed with no license documentation
*(apps-drivers, Medium)* All 27 SVGs in `assets/fa-icons/` carry the "Font Awesome Pro 7.3.0 … (Commercial License) Copyright 2026 Fonticons, Inc." stamp (`assets/fa-icons/lock.svg:1`), and both apps ship derivatives. FA Pro permits embedding in apps but forbids hosting Pro icon *source* files in a publicly accessible repo/package. The repo is private today (`isPrivate=true`), but it is licensed FSL-1.1-ALv2 (source-available, with an Apache-2.0 future grant that purports to sublicense contents Fonticons owns), the marketing direction references the repo publicly, and the bearer/SDK packages are designed as independently-publishable. There's no `LICENSE`/`README` in `assets/fa-icons/` and the Android vector XMLs carry no attribution. **Next step:** add `assets/fa-icons/README.md` documenting the FA Pro seat + terms, and add the directory + derived `ic_fa_*` assets to a pre-public checklist to strip or swap several icons (lock, camera, chevron-left, arrows-rotate exist in FA Free) before any repo-public or package-publish step.

### Shared BLE bearers dropped the advertiser self-heal on both platforms
*(bearers, Medium)* ble-lab/SPEC.md:227,409 requires a periodic tick self-heal (`if ticks % 30 == 0 startAdvertise()`); the legacy Android call is gated `!useSharedBearers` (`HopBearer.kt:364-365`) so it's dead on the default path. The shared Android `BleBearer.startAdvertise()` is commented "§7.1 idempotent self-heal — recovers a wedged advertiser" but its only caller is `onServiceAdded` (`BleBearer.kt:348,388-401`) — nothing periodic re-arms it; `onAdvertisingSetStopped` clears `advSet` with no re-arm. On Apple, `didPublishL2CAPChannel` error → log+return (undiscoverable, no retry, `swift:322-323`), advertising-start error → log-only (`swift:335-337`), and `willRestoreState` is a no-op whose own comment cites the SPEC R10 requirement it doesn't implement (`swift:362-365`). Bonus: Android `Peripheral.stop()` never shuts down `beaconSched`, so the cycler restarts the iBeacon advertiser after the bearer is stopped (`BleBearer.kt:331-340` vs `422-430`). Android is the broader exposure (a wedged/stopped advertising set or BT toggle → undiscoverable-as-peripheral until app restart). **Next step:** wire the spec-mandated periodic `startAdvertise`/`startBeacon`/republish-L2CAP self-heal into each shared bearer, retry failed publishes with backoff, and cancel `beaconSched` in `Peripheral.stop()`.

### Relay bearer reconnect policy invites synchronized storms
*(bearers, Medium)* Both `RelayBearer`s reset backoff to the 1s minimum on socket-open, not after proven stability (Apple `swift:144`, Android `kt:101`) — the BLE bearer got this right with a 30s `stableUp` rule the relay bearer lacks. A relay that accepts then immediately drops (overloaded `maxScale=1` Cloud Run, the fleet's observed 429/wake-churn regime) is re-dialed at ~1s forever. Android has NO jitter (`kt:128-133`) while Apple adds 0–1s, so an Android sub-fleet reconnects in lockstep — and every push-to-main redeploy drops all fleet WebSockets simultaneously, exercising this on every deploy. Neither inspects the HTTP upgrade status, so a 429/Retry-After is treated as any failure (`kt:115-117` discards the OkHttp `Response`). Apple detail: `dial()` with an unparseable relayURL silently returns with `started=true`, never retries or logs (`swift:88`). **Next step:** reset backoff only after N seconds of stable connection (mirror BLE `stableUp`), add jitter on Android, and parse the upgrade `Response` for 429/Retry-After.

### LAN discovery is one-shot on both platforms — a transient resolve/dial failure loses the peer until mDNS re-announces
*(bearers, Medium)* Dials fire only on discovery-change events (Apple `browseResultsChangedHandler`, Android `onServiceFound`). On Android, `onResolveFailed` (NSD error 3/busy is common) and a failed TCP connect both just `dialing.remove` and return with no retry (`bearer-lan/LanBearer.kt:331-334,350-357`); `onServiceLost` is empty (`kt:294`), so no lost→found churn. Apple has the same shape (`swift:245-257`). With Wi-Fi Direct removed, LAN is the only Wi-Fi transport for Android↔Android, so a single transient failure during startup/doze permanently forfeits the high-bandwidth LAN path for the session (the greater-id tiebreaker means the other peer won't dial either), leaving BLE as the only fallback. BLE re-dials on every advert sighting; LAN lacks that pressure. **Next step:** on resolve/dial failure schedule a backoff retry, or periodically re-walk the current browse/NSD result set against `linksByPeerId`.

### `hop_node_open` / corrupt hop.db silently falls back to in-memory storage, contradicting the documented contract
*(merged: sdk-abi + persistence-upgrade-compat, Medium)* `HopNode::open` does `SqliteStore::open(&db_path).or_else(|_| SqliteStore::open_in_memory())` (`core/hop/src/lib.rs:423-426`), so a bad/read-only/corrupt/future-incompatible path yields a working-looking node whose sessions, pending sends, and custody bundles silently evaporate on restart — and nothing repairs or deletes the bad file, so every subsequent launch takes the same silent fallback forever. `sdk/hop.h:31` and both wrappers document "NULL only on a NULL/invalid path" — the opposite; `cabi.rs` returns NULL only for NULL/non-UTF-8 strings. There's no `is_persistent` signal for the host to detect the downgrade, and the on-device hop.db is the declared ground truth for the external test harness, so an in-memory node also makes the harness lie. Constructors also `.expect()` inside `extern "C"` fns (aborts across FFI), though that's near-unreachable. **Next step:** on open failure, delete/rename the bad db and re-open persistent (fresh state beats permanent amnesia), surface the event via a status flag/return value, `catch_unwind` the C constructors, and regen the header to match.

### hop.db is plaintext (ratchet keys, topic keys, message bodies) despite an in-code claim that it is encrypted
*(persistence-upgrade-compat, Medium)* The driver comment asserts "The encrypted hop.db has no plaintext mirror" (`HopBearer.swift:1815`), but `rusqlite` uses `features=["bundled"]` (plain SQLite, not SQLCipher; `Cargo.toml:40`), the store doc says encryption is "layered at open time" while nothing layers it (`hop-store-sqlite/src/lib.rs:12-13`), and `HopNode.open` passes the raw path straight through with no cipher param. So the kv table holds double-ratchet root/chain/skipped keys (`session.rs:64-76`), hps content keys + signing seeds (`hps.rs:82-99`), and plaintext outbound bodies (`PendingContent.body`) in cleartext — plus the driver writes a plaintext `messages.json` mirror anyway. DESIGN.md §13.2 marks "Encryption at rest via SQLCipher or app-supplied page encryption" as "DECIDED & IMPLEMENTED," and §33 builds a data-protection argument on at-rest exposure being "essentially nil." iOS file protection + sandboxing mitigate, but the project's own `devicectl` db-pull workflow trivially extracts live forward-secrecy key material. **Next step:** minimum — correct the three false/misleading statements and record an explicit decision; full fix — ship `rusqlite` `bundled-sqlcipher` keyed from Keychain/Keystore as the decided design already specifies.

### Persisted bundles cross wire-format changes unguarded (on-disk decode)
*(persistence-upgrade-compat, Medium; shares root cause with #4)* The `bundles` table stores raw postcard `Bundle` bytes. Two incompatible layout changes shipped in the deployed window (`56982da` inserted `private` into the middle of `SignedInner`; `5dd64d3` shifted `Destination` indices) with `BUNDLE_VERSION` unbumped and unread. After an in-place upgrade, previously-persisted bundles fail `Bundle::from_bytes`: `Store::get` returns `None` (`lib.rs:88-97`), `rehydrate` skips them (`node.rs:799-800`) so the device's own undelivered messages silently stop retransmitting, and `have()` still advertises the undecodable ids (`lib.rs:119-133`) — though the actual offer path filters through `get` first, so those aren't wire-visible ghost offers, and rows are still pruned on `seen.expires_at`. The 06-29 `Destination` shift's on-device impact was masked only by the same-day app-id rename giving fresh data dirs, which won't repeat. **Next step:** read `inner.version` (or a format-epoch kv) on decode and reject-and-delete stale rows so a breaking change fails loudly and cleanly rather than silently eating the queue.

### Firestore `presence` collection is a permanent per-device location log — no `expireAt`, no TTL policy, never deleted
*(services-infra, Medium)* `presence` docs map a device's base58 *address* → last-seen region + `heartbeatAt`, written on every check-in (`main.rs:929-937`). `presence_doc_json` writes no `expireAt` timestampValue (`hop-store-firestore/src/lib.rs:662-670`), `infra/firestore.tf` has exactly one TTL policy (on `bundles`), and `store.remove` doesn't touch presence, so the cloud keeps an indefinitely-retained, queryable per-address→region timeline forever — the dataset DESIGN §33 (lines 1755-1757, 1766-1767) calls "the most sensitive dataset" and claims storage-limitation is "built in, not bolted on" via presence staleness (which is only a 90s read-side filter, `PRESENCE_TTL_MS`, not deletion). Same gap on `registry` docs (bounded ~42, freshness-filtered). **Next step:** stamp `expireAt = heartbeat + small multiple of PRESENCE_TTL_MS` on presence + registry docs and add `google_firestore_field` TTL resources; the read path already ignores stale presence, so TTL deletion can't regress routing.

### Relay "durable mailbox" can drop last-moment bundles on scale-to-zero
*(services-infra, Medium)* `FirestoreStore` accepts bundles into memory and mirrors to Firestore from a background thread over an unbounded mpsc channel, "best-effort … the hot path never blocks" (`lib.rs:59-75`), while the module doc sells it as the durable mailbox that "survives scale-to-zero" (`lib.rs:3-4`). The fleet runs `min_instance_count=0` with `cpu_idle=true` (`cloud_run.tf:26,84`), so when the last WebSocket drops CPU is throttled immediately and relayd has no SIGTERM/shutdown handler (grep = 0 hits), so pending `Op::Write` mirrors and the 20s-interval spool/handoff writes die with the reaped process. ### Kotlin `HopNode` is leak- and use-after-free-prone
*(sdk-abi, corrected Low)* `sh.hop.HopNode` owns a raw `Pointer` with a bare `fun free()` (`Hop.kt:100`), implements neither `AutoCloseable` nor a `Cleaner`, and never nulls `raw` after free, so a dropped node leaks the Rust node + SQLite store and any post-free call passes a dangling pointer. The Swift wrapper avoids this with `deinit` (`Hop.swift:57`) — an asymmetry between the two template wrappers. `hop.h:22` calls `HopNode` "reference-counted" but exports no `clone`/`retain`, so concurrent `hop_node_free` vs `hop_node_tick` is an unavoidable UAF with no documented synchronization rule. Not exercised in production today (the shipped app drives the node via UniFFI's `AutoCloseable`+`Cleaner` bindings; the `sh.hop` driver never calls `free()`), which caps it at Low. **Next step:** make Kotlin `HopNode : AutoCloseable` with an idempotent `close()` that nulls the pointer (+ `Cleaner` backstop); either export `hop_node_clone` or amend `hop.h` docs to state `free` must be externally synchronized.

### `hop.h` has no ABI version symbol or negotiation
